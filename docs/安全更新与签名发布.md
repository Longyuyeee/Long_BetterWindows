# 安全更新与签名发布

## 目标与边界

Long助手的应用更新链路负责自动发现 GitHub Release、验证发布清单签名并下载完整性通过的 ZIP。当前便携式分发模式下，软件不会静默替换正在运行的目录，也不会自动执行网络下载的程序；用户确认后再完成版本替换。

这条链路解决的是“下载内容是否由项目维护者授权、是否被篡改”。Windows Authenticode 仍是独立的发布者身份能力，当前 RC 通道尚未配置商业代码签名证书。

## 信任链

1. 发布者在本机生成 3072-bit RSA 密钥对。
2. 私钥仅保存在仓库根目录的 `local-secrets/update-signing/update-signing.private.key`。
3. Git 通过 `local-secrets/` 和 `*.private.key` 双重规则忽略私钥。
4. 公钥写入 `src/LongBetterWindows.Host/Update/update-public-key.xml`，随应用发布。
5. Release 包构建完成后生成 `update-manifest.json`。
6. 发布脚本使用 RSA + SHA-256（PKCS#1 v1.5）生成分离签名 `update-manifest.sig`。
7. 客户端从 GitHub Release API 发现版本，只接受配置仓库内的 HTTPS 资源。
8. 客户端验证清单签名、版本、通道、提交、资源 URL、文件大小与 SHA-256。

## 本机密钥

首次生成：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\new-update-signing-key.ps1
```

生成后必须确认：

```powershell
git check-ignore -v local-secrets\update-signing\update-signing.private.key
git ls-files local-secrets
```

第二条命令必须没有输出。私钥文件的 ACL 只授予创建它的 Windows 账户。

私钥不应通过 Git、Release、聊天、日志或普通云盘传输。换机时应使用受控的加密介质或密码管理器附件单独迁移，并在新机器上再次检查 ACL。

## 构建并签署候选

先保证源代码已提交，随后执行：

```powershell
.\release.ps1 -Version 1.11.0-rc.1
.\sign-update-manifest.ps1 `
  -ReleaseDirectory .\artifacts\releases\v1.11.0-rc.1 `
  -Tag v1.11.0-rc.1
```

上传到同一个 GitHub Release 的更新资源至少包括：

- `LongBetterWindows-v<version>-win-x64-self-contained.zip`
- `LongBetterWindows-v<version>-win-x64-framework-dependent.zip`
- `SHA256SUMS.txt`
- `release-manifest.json`
- `update-manifest.json`
- `update-manifest.sig`

签名清单中的 `source_commit` 必须是 Release 标签指向的提交；发布后不得修改相同标签下的文件。

## 密钥轮换

不要在普通版本发布中使用 `-Force` 重建密钥。轮换会让旧客户端无法验证只由新密钥签署的更新。

计划轮换应经过过渡版本：

1. 用旧密钥签署一个同时内置新公钥的版本。
2. 等待主要用户完成过渡更新。
3. 后续版本改由新私钥签署。
4. 将旧私钥离线封存，并记录停用时间。

若私钥疑似泄露，应立即停止自动更新发布、撤回受影响 Release、发布安全公告，并通过可信人工下载渠道分发内置新公钥的恢复版本。
