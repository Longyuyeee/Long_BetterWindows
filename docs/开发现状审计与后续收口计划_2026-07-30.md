# Long助手开发现状审计与后续收口计划

审计日期：2026-07-30

审计分支：`agent/window-manager-transactional`

审计源码基线：`baed13431d132cffff3082ee84073c1ea6171363`

当前候选版本：`1.11.0-rc.2`

协作入口：Draft PR [#12](https://github.com/Longyuyeee/Long_BetterWindows/pull/12)

## 1. 结论

Long助手已经基本对齐最初确定的产品方向：

- 产品定位已经稳定为 Windows 统一效率入口，参考 uTools 的入口、搜索、命令和插件交互逻辑，但不承担 uTools 插件兼容。
- 主界面、命令面板、插件市场、设置、主题、动效、响应式布局、DPI 与辅助功能工程门禁均已形成体系。
- 25 个正式内置插件、42 条命令已经进入统一 Manifest、权限、生命周期、质量和发布证据链。
- Web、C# Script、Native、Hybrid 四种插件运行时已经具备脚手架、生产验证、确定性打包与分发资格判定。
- Web SDK、.NET Contracts SDK、无宿主测试 SDK 和 WPF UI Kit 均已落盘到 `v1.0.0` 边界。

但当前仍不能声明“完全收口并可正式发布”：

1. `QuickLaunchPlugin` 仍直接引用 Host 内的搜索 DTO、`ISearchProvider` 与结果动作合同，是最后一项原生插件宿主编译耦合。
2. 25 项真实桌面插件人工验收仍为 `0 passed / 25 pending / 0 failed`，所以发布判断必须保持 `release_eligible=false`。
3. 物理 DPI、任务栏行为、辅助功能/读屏、管理员性能采集、真实下载与干净 Windows、生产 Registry/CDN 回滚等外部门禁尚未全部签核。
4. Draft PR 当前可干净合并，但 GitHub 没有报告自动 Checks；质量结论主要依赖本地门禁，仓库级持续集成仍有缺口。

因此，当前阶段定义为：**产品与主要工程目标基本对齐，代码侧接近收口，尚未达到正式发布收口。**

## 4. 仍未关闭的风险

### P0：发布阻断项

- 25 / 25 正式插件必须在真实桌面逐项完成人工正向验收，并生成与源码、宿主和证据哈希绑定的回执。
- 任务栏分组、固定/取消固定、多窗口身份需要在真实 Windows 任务栏观察。
- 100%、125%、150%、200% 等物理 DPI、多显示器、跨屏定位与取色需要实机确认。
- 高对比度、Reduced Motion、键盘完整操作、Narrator/NVDA 语义需要人工确认。
- 管理员权限下的 WPR/WPA 原生性能归因需要补齐。
- GitHub 真实下载、干净 Windows 安装/升级/卸载、SmartScreen/杀毒提示需要签核。
- 生产 Registry/CDN 的发布、失败恢复和回滚需要在受控凭据环境演练。

这些项目不能由单元测试、截图模拟或文档勾选替代。

### P1：代码与平台收口项

- 把公共搜索 DTO、Provider 和结果动作合同迁入 Contracts SDK。
- 迁移 QuickLaunch 并使 `host_coupled_projects` 变为空数组。
- 为仓库自身建立 GitHub Actions 必需检查，至少覆盖 Release 构建、全量测试、边界清单与关键插件验证。
- 完成 PX3D 总审计：程序集所有权、加载上下文共享程序集规则、API 版本和包结构不得漂移。
- 明确三个 .NET 包和 Web SDK 是仅仓库内版本化，还是发布到公共包源；当前只验证了包结构，没有发布公共 NuGet/npm。

### P2：发布后增强项

- 扩展 Long Plugin UI Kit 的 Web/WPF 组件覆盖、视觉回归与无障碍样例。
- 统一插件目录、市场 Registry 和文档元数据来源。
- 评估 Script/Native 的独立进程隔离、CPU/内存配额、崩溃恢复与高风险能力二次确认。

P2 不应阻塞当前 unsigned 主产品进入人工验收，也不应在 P0/P1 关闭前大规模扩张范围。

## 5. 后续开发计划

### 阶段 A：PX3D-C 清零原生插件宿主耦合

实施内容：

1. 在 Contracts SDK 中定义稳定的搜索 Query、Result、Result Action 与 Provider 合同。
2. 让 Host 搜索编排层单向依赖 SDK 合同。
3. 迁移 `QuickLaunchPlugin`，删除其 Host 项目引用。
4. 增加程序集归属、能力映射、无宿主合同测试和机器审计回归。

退出条件：

- `docs/native-plugin-boundary-audit.json` 的 `host_coupled_projects` 为空。
- 八个原生生产组件全部只依赖正式 SDK/WPF UI Kit 或自身依赖。
- Release 构建零警告零错误、全量测试全通过、四运行时矩阵 4 / 4。

### 阶段 B：PX3D 总收口与仓库 CI

实施内容：

1. 对 Web SDK、Contracts SDK、Testing SDK、WPF UI Kit 做统一版本与包结构审计。
2. 固化 Loader 共享 SDK 程序集规则，避免插件目录私有副本造成类型身份分裂。
3. 将 Release 构建、全量测试、原生边界、Manifest/Validator 和关键插件矩阵接入仓库 GitHub Actions。
4. 更新模板、开发指南、API 兼容策略和变更流程。

退出条件：

- Draft PR 出现必需且通过的自动 Checks。
- SDK API 版本、程序集版本、Manifest `min_api_version` 与包版本可自动交叉验证。
- 新建插件可以从模板到测试、验证和打包完整走通，无需引用 Host。

### 阶段 C：用户与受控环境验收

按 [`用户最终验收操作手册.md`](用户最终验收操作手册.md) 和 [`发布候选检查表.md`](发布候选检查表.md) 执行：

1. 完成 25 项插件真实桌面验收。
2. 完成任务栏、物理 DPI、辅助功能/读屏和管理员性能门禁。
3. 完成真实下载与干净 Windows 安装、升级、卸载。
4. 使用受控生产凭据完成 Registry/CDN 发布与回滚演练。

退出条件：

- 所有必需人工项都有不可覆盖证据与独立批准。
- 最终聚合报告为 `release_eligible=true`。

### 阶段 D：冻结并重建发布候选

实施内容：

1. 冻结干净提交，不再混入功能开发。
2. 从冻结提交重新生成安装包、便携包、校验和与 Release Manifest。
3. 先执行最终门禁 `-PreflightOnly`，再生成正式发布决策。
4. 审核无误后创建新的 GitHub Prerelease/Release。

退出条件：

- Git 标签、源码提交、安装包、ZIP、Manifest 和 SHA-256 全部一致。
- 发布说明准确披露 unsigned/signed 通道和已知限制。

## 6. 需要用户参与或决定的事项

进入阶段 C 前后，需要用户提供：

1. 在真实 Windows 设备上按手册完成桌面、DPI、任务栏和辅助功能验收。
2. 决定 SDK 是否发布到公共 NuGet/npm；若暂不发布，则明确为仓库内 SDK。
3. 决定当前继续采用公开 `unsigned` 通道，还是准备正式代码签名证书切换 `signed` 通道。
4. 在不提交密钥的前提下，提供或配置生产 Registry/CDN 凭据并参与回滚演练。
5. 最终确认候选是否可以从 Prerelease 提升为正式 Release。

## 7. 下一步建议

下一开发批次固定为 **PX3D-C：QuickLaunch 搜索合同迁移**。完成后立即做 PX3D 总收口和仓库 CI，不再增加新的用户功能；随后把主工作面转交给用户的物理桌面与发布环境验收。

只有阶段 A、B 的代码门禁和阶段 C 的人工门禁全部关闭后，项目才可以从“接近收口”改判为“完成收口、可正式发布”。
