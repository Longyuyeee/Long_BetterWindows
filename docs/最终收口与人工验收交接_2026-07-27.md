# Long助手最终收口与人工验收交接

## 当前判断

产品方向、核心功能、插件架构、更新安装链路和可自动验证的故障边界已经进入冻结状态。此后不再扩展功能；剩余工作只包括真实桌面体验、管理员诊断、外部凭据环境和干净候选发布。

面向实际验收人的逐项操作、风险提醒、25 插件检查表和证据命令见 [用户最终验收操作手册](用户最终验收操作手册.md)。本文件保留工程交接和发布顺序口径。

根目录 `verify-final-closure.ps1` 是统一入口。它只执行 Release 构建、全量测试、插件矩阵校验和 WPR 权限预检，不移动窗口、不注入输入、不改剪贴板、不修改系统设置，也不请求 UAC。

正式检查：

```powershell
.\verify-final-closure.ps1 `
  -OutputPath "artifacts/quality/final-closure/report.json" `
  -RequireHumanValidationReady
```

报告中的 `ready_for_human_validation=true` 表示机器侧已经收口，可以开始以下人工流程；它不表示 `release_eligible=true`。

## 需要用户完成的验证

### 1. 25 个插件正向功能

按 [插件人工证据验收](插件人工证据验收.md) 从低风险到关键桌面副作用依次执行。每项只在实际操作、查看原始证据并确认结果后生成回执。

重点观察：

- 主题、键盘路径、复制按钮、错误提示和窗口关闭；
- Screenshot/ColorPicker 的 Overlay、Esc 取消与真实剪贴板结果；
- WindowManager 的最小化/最大化、多显示器、置顶和高权限拒绝；
- Macro 的 F6/F7/F8、单次/循环停止和无残留按键/鼠标按钮。

### 2. 任务栏视觉

至少打开两个不同插件的分离窗口，确认：

- 图标、标题和任务栏分组可区分；
- 固定、取消固定及重新打开不会串到其他插件；
- 关闭分离窗口后焦点正确返回 Long助手或原应用。

机器侧 25 个 HWND 身份和图标唯一性已经通过；这里仅判断 Explorer 的最终视觉行为。

### 3. 物理 DPI 与辅助功能

分别执行：

- [物理 DPI 发布验收](物理_DPI_发布验收.md)：100%、125%、150%、200%，亮色和暗色；
- [辅助功能发布验收](辅助功能发布验收.md)：高对比度、减少动画、组合模式，以及至少一次 Narrator 或 NVDA 公告。

脚本不会替用户切换 Windows 设置，也不会自动批准截图。

两类证据汇总后，最终 `verify-external-release-gate.ps1` 只接受 schema v2：物理 DPI 必须为 100%、125%、150%、200% 四档各 8 张、总计 32 张；辅助功能必须包含三种配置并至少有一次 Narrator/NVDA 批准。旧摘要、缺档、计数不符或无读屏批准会在生成最终发布决策前被拒绝。

### 4. 管理员 WPR/WPA

在管理员 PowerShell 按 [原生性能 WPR 采样验收](原生性能_WPR_采样验收.md) 采集 `CPU.Light + DesktopComposition.Verbose`，随后在 WPA 检查 CPU Usage (Sampled) 与 Desktop Composition。原始 ETL 保留本地，不上传仓库。

严格 `<200 MB` 工作集已经在干净提交的 5×9 秒样本中通过；WPR 用于确认没有未解释的原生持续负载。

### 5. 干净 Windows 与真实下载

在新用户、一次性 VM 或另一台干净 Windows 10/11 机器执行：

1. 从 GitHub Release 下载 unsigned Setup.exe；
2. 记录浏览器下载、SmartScreen 和杀毒软件提示；
3. 完成安装、首次启动、托盘、全局热键和 WebView2 检查；
4. 覆盖升级后确认设置与插件数据保留；
5. 卸载并确认快捷方式、安装目录及预期保留数据行为。

操作人与最终批准人必须不同，使用仓库现有下载和干净环境批准脚本生成证据。

### 6. 真实 Registry/CDN 演练

需要维护者在受控凭据环境注入真实 HTTPS Registry/CDN、发布者信任库和部署令牌，完成 Dry Run、部署、公开验证、回滚和回滚后验证。凭据和私钥不得提交。

演练摘要使用 schema v2，并哈希锁定 `preflight-dry-run.json`、`baseline-verification.json`、`deployment.json`、`deployed-verification.json` 和 `rollback-verification.json`。最终门禁会从摘要同目录重新计算五份哈希；旧摘要、文件缺失或内容变化均拒绝。

## 最终发布顺序

1. 在当前收口分支完成 25 项插件功能与主观体验验收；修复期间不生成正式设备证据。
2. 第一轮无代码问题后冻结源码，将 Draft PR 合入 `master` 并固定最终提交。
3. 在最终提交上运行 `verify-final-closure.ps1`，统一版本号并生成新的 unsigned RC、Setup.exe、Manifest 与 SHA-256。
4. 对该最终提交和候选完成任务栏、DPI、辅助功能、WPR、真实下载和干净 Windows 正式证据。
5. 完成真实 Registry/CDN 部署回滚演练和外部门禁聚合。
6. 复核远端 Release 资产摘要后再决定是否转为稳定版。

任何一步失败都回到对应项修复；不要在旧 `v1.11.0-rc.2` 目录或标签上覆盖文件。

新候选 Release Manifest 使用 schema v1。最终门禁要求 `source_dirty=false`、有效版本与 `win-x64` runtime，并逐项核对包名、种类、SHA-256、字节数、25 个插件 Manifest/唯一 ID、42 条命令、命令冒烟和 WebView2 清理结果。缺少 schema 的历史 Manifest 只能作为历史记录，不能复用到新最终决策。

最终聚合时，Manifest 必须与全部候选 ZIP 保持在同一目录。聚合器会重新读取每个 ZIP 并复算实际字节数和 SHA-256；缺失、截断或替换任一包都不会生成最终决策。
