> 审计日期：2026-07-28
>
> 审计对象：用户提供的 uTools 管理中心截图、uTools 官方使用文档、Long 当前 `master` 源码
>
> 本批开发基线：`ddb1d14`，`master` 与 `origin/master` 同步
>
> 文档性质：交互架构决策与后续开发基线，不复制 uTools 视觉、品牌、插件协议或商业功能

> 交互细节、点击语义、键盘层级、焦点恢复和 P0 验收场景见 [`统一工作区交互细节审计与验收规范_2026-07-28.md`](统一工作区交互细节审计与验收规范_2026-07-28.md)。

## 1. 本次校正结论

用户指出的关键事实成立：uTools 的“管理中心”不是脱离主产品的传统后台，而是统一应用壳层中的一个模块。进入管理中心后，插件应用市场、已安装插件、插件设置和插件运行仍处于同一套模块导航、搜索、返回和窗口生命周期中。

Long 当前虽然已经具备命令中心、ToolCenter、插件市场、嵌入式插件和分离窗口，但这些能力仍由多个互相替换或互相唤起的界面承担，缺少统一的模块会话。由此造成的主要体验差距不是颜色或间距，而是：

1. 用户从命令中心进入管理、市场或插件后，任务上下文被切断。
2. ToolCenter 的页面只是固定区域显隐，不是可寻址、可恢复、可关闭的模块。
3. 嵌入式插件会整块替换 ToolCenter，返回后只能回到笼统的管理界面。
4. 插件分离是窗口操作，不是同一个模块实例在嵌入态与分离态之间迁移。
5. 搜索框、左侧插件目录和当前内容没有形成清晰的作用域关系。

因此，下一阶段不应继续给现有页面叠加局部按钮，而应先建立统一工作区 Shell 和模块会话模型，再迁移管理中心、市场与插件。

## 2. uTools 交互证据

### 2.1 截图信息架构

用户提供的截图可拆成四层：

1. **顶部模块条**：根模块为“管理中心”，其后打开“插件应用市场”子模块；子模块可关闭。
2. **顶部作用域搜索**：当前搜索对象是插件应用市场，不是全局命令搜索。
3. **左侧已安装应用目录**：在管理工作区内持续存在，承担插件识别、选择和运行入口；底部保留个人中心与设置。
4. **主内容宿主**：当前渲染市场内容，后续可切换为插件设置、详情或其他管理模块。

这是一套“稳定壳层 + 可变模块”的结构，不是“左侧菜单 + 多个管理页面”的普通后台结构。

### 2.2 官方行为核对

- uTools 官方说明可通过搜索框头像或搜索“插件应用市场”进入市场；左侧显示已安装插件，双击可打开插件应用：[插件应用市场](https://www.u-tools.cn/docs/guide/plugin-store.html)。
- 选中已安装插件后会展示插件设置、功能关键字和使用说明，说明“插件目录”和“插件管理详情”位于同一管理工作区：[插件应用市场](https://www.u-tools.cn/docs/guide/plugin-store.html)。
- 插件界面顶部继续显示应用名称、触发关键字及设置菜单；`Esc` 退出插件，`Ctrl+D` 可分离插件：[插件应用界面](https://www.u-tools.cn/docs/guide/plugin-interface.html)。
- 插件还可以向搜索面板推送内容并参与后续搜索，说明插件运行与统一输入入口不是两套互不相干的系统：[插件应用界面](https://www.u-tools.cn/docs/guide/plugin-interface.html)。

### 2.3 可借鉴与不可复制

Long 应借鉴：

- 管理中心也是模块；
- 模块共享导航、搜索、返回和生命周期；
- 已安装插件是稳定目录，不只是管理卡片集合；
- 插件设置、插件运行和市场属于同一工作区模型；
- 嵌入与分离保持同一个插件会话。

Long 不复制：

- uTools 的图形标识、圆角造型、颜色、排版和动效；
- uTools 插件 API、Manifest、包格式和运行时；
- 会员、支付、评论、账号商业体系；
- 截图中的具体市场内容与素材。

## 3. Long 当前实现审计

### 3.1 已有能力

Long 已经具备构建统一工作区所需的大部分业务能力：

- 命令中心、上下文快照、统一搜索结果和插件命令；
- ToolCenter 的概览、工作流、插件、市场、系统、诊断、开发者和设置页面；
- 插件生命周期、嵌入式内容、分离窗口和任务栏身份；
- 市场安装、升级、降级、卸载、签名校验和会话协调；
- Long Design System、主题同步、国际化和可访问性基础；
- 延迟加载、页面回收和严格内存门禁。

这些能力应保留并迁移，不需要重新实现插件系统或市场事务。

### 3.2 结构性差距

#### A. 主窗口采用整块替换

`MainWindow.xaml` 同时放置 `ToolCenterControl` 和 `EmbeddedPluginSurface`。打开嵌入式插件时，`MainWindow.xaml.cs` 的 `ShowEmbeddedPlugin` 会隐藏 ToolCenter 并显示插件区域；关闭或分离后再反向切换。

影响：

- 当前管理页面、滚动位置和选择状态不是正式导航状态；
- 不能同时维护“管理中心 > 市场 > 插件详情 > 插件运行”的历史；
- 返回语义依赖当前控件是否可见；
- 新模块继续增加时，主窗口事件与显隐分支会持续膨胀。

#### B. ToolCenter 是固定页面切换器

`ToolCenterControl.xaml.cs` 的 `ShowPage(string page)` 内部硬编码八个页面，并逐个设置 `Visibility`。`Ctrl+Tab` 也只循环这些固定字符串。

影响：

- 页面没有稳定的模块键、参数和实例身份；
- 无法表达 `plugin-settings:<pluginId>`、`plugin-runtime:<sessionId>` 等动态页面；
- 已打开模块不能去重、激活、关闭或恢复；
- 没有后退/前进栈；
- 搜索无法随模块切换作用域。

#### C. 插件管理页不是应用目录

`PluginManagementControl` 将插件作为主内容区中的管理卡片展示。离开插件页时，`ReleasePluginManagementPage` 会释放整个页面。

影响：

- 插件目录不能在市场、插件设置和插件运行之间持续存在；
- 插件选择、筛选和滚动位置容易丢失；
- “选择插件查看设置”和“打开插件运行”没有形成一致路由；
- 页面释放策略与插件运行生命周期容易混淆。

#### D. 市场仍是 ToolCenter 的一个页面

`MarketplaceControl` 业务事务已经较完整，但它只在 `market` 固定页下延迟创建，搜索框也封装在页面内部。

影响：

- 市场不能作为可关闭、可返回的模块；
- 顶部无法显示当前搜索作用域；
- 安装后对左侧插件目录、插件设置模块的刷新没有统一协调入口；
- 当前偏展示型的首屏结构不利于高频扫描、搜索和管理。

#### E. 插件嵌入与分离没有模块实例契约

现有按钮能打开、关闭和分离插件，但主窗口只保存当前嵌入内容，尚未形成“同一个插件会话在嵌入态与分离态之间迁移”的通用模型。

影响：

- 后续容易重复创建 WebView2 或原生视图；
- 分离/返回时可能丢失输入、滚动位置和页面状态；
- “关闭视图”“结束插件运行”“后台继续”容易被混成同一动作。

## 4. 与最初设计的对齐判断

### 4.1 保持对齐的部分

最初 UI/UX 规范已经明确：

- Command Palette 专注快速执行；
- ToolCenter 专注管理与配置；
- 用户只需记住一个入口；
- 插件能力通过宿主统一注册；
- 宿主负责插件窗口外壳、主题、安全区域和生命周期；
- 插件执行后应正确返回原工作状态。

本次方案不推翻这些职责，而是补足它们之间缺失的导航与会话层。

### 4.2 需要修正的理解

“命令中心专注执行、ToolCenter 专注管理”不等于二者必须是互相割裂的窗口和状态树。更准确的产品模型应为：

- **Launcher Mode**：紧凑、临时、以输入和结果为中心，用于快速唤起和执行。
- **Workspace Mode**：扩展、持久、以模块和任务连续性为中心，用于管理、市场、插件设置、插件运行和复杂工作流。

两种模式可以有不同尺寸和布局，但必须共享：

- 模块标识；
- 导航意图；
- 插件会话；
- 搜索上下文；
- 返回位置；
- 主题、权限与生命周期服务。

这与最初“统一入口”和“统一窗口宿主”的设计目标一致，比当前多个窗口相互唤起的实现更接近原始愿景。

## 5. 目标架构

### 5.1 Shell 组成

```text
LongApplicationShell
├─ LauncherSurface
│  ├─ GlobalInput
│  ├─ ContextChips
│  └─ SearchResults
└─ WorkspaceSurface
   ├─ ModuleStrip
   ├─ ContextualRail
   ├─ ScopedSearch
   └─ ModuleContentHost
```

Launcher 与 Workspace 是同一应用 Shell 的两种呈现状态，不要求在同一个固定矩形中同时显示。

### 5.2 模块身份

每个模块必须由“类型、业务键、实例键”共同标识，禁止只用页面字符串：

```text
management:root
marketplace:catalog
plugin-settings:<pluginId>
plugin-runtime:<pluginId>:<sessionId>
workflow:<workflowId>
settings:root
diagnostics:root
developer:root
```

默认规则：

1. 单实例模块再次打开时激活已有实例。
2. 插件运行模块是否允许多实例由 Manifest 与宿主策略共同决定。
3. 关闭活动模块后激活最近一个仍有效的模块。
4. 根管理模块不可被普通关闭动作移除。
5. 模块视图释放与插件运行停止是两个不同操作。

### 5.3 核心契约建议

```csharp
public readonly record struct WorkspaceModuleKey(
    string Kind,
    string ResourceId,
    string? InstanceId = null);

public sealed record WorkspaceModuleDescriptor(
    WorkspaceModuleKey Key,
    string Title,
    string? IconKey,
    bool CanClose,
    bool SupportsDetach,
    string? SearchScopeId);

public interface IWorkspaceModule
{
    WorkspaceModuleDescriptor Descriptor { get; }
    object View { get; }
    ValueTask ActivateAsync(CancellationToken cancellationToken);
    ValueTask DeactivateAsync(CancellationToken cancellationToken);
    ValueTask CloseAsync(CancellationToken cancellationToken);
}

public interface IWorkspaceSearchScope
{
    string Placeholder { get; }
    Task<SearchBatch> SearchAsync(
        string query,
        CancellationToken cancellationToken);
}
```

建议新增：

- `WorkspaceNavigationState`
- `WorkspaceSessionCoordinator`
- `IWorkspaceModuleFactory`
- `IWorkspaceModuleRegistry`
- `IWorkspaceSearchScope`
- `PluginWorkspaceSession`
- `WorkspaceDetachCoordinator`

这些类型应位于无 WPF 依赖的宿主应用层；WPF 只负责绑定状态、承载视图和执行窗口操作。

### 5.4 导航状态机

```text
Launcher
  ├─ open management ──> Workspace(management:root)
  ├─ open marketplace ─> Workspace(management:root, marketplace:catalog)
  └─ run plugin ───────> Workspace(plugin-runtime:...)

Workspace
  ├─ select installed plugin ─> plugin-settings:<id>
  ├─ run plugin ──────────────> plugin-runtime:<id>:<session>
  ├─ detach ──────────────────> Detached(same session)
  ├─ reattach ────────────────> Workspace(same session)
  ├─ close module ────────────> previous valid module
  └─ Esc ─────────────────────> close transient layer / back / return focus
```

### 5.5 搜索作用域

| 场景 | 搜索范围 | 结果行为 |
|---|---|---|
| Launcher | 全局命令、应用、文件、插件数据 | 执行或打开模块 |
| 管理中心 | 设置、管理目的地、已安装插件 | 打开对应模块 |
| 插件市场 | 市场目录 | 打开市场详情或安装 |
| 已安装应用目录 | 本机插件列表 | 选择、运行或查看设置 |
| 插件运行 | 插件声明的数据源 | 推送内容或继续搜索 |

顶部搜索框的占位文字、Provider 和结果动作必须由活动模块声明，不能继续由每个页面私自实现一套互不感知的搜索状态。

### 5.6 已安装插件目录

管理工作区左侧目录应具备：

- 插件图标、名称、运行状态和更新状态；
- 搜索与必要筛选；
- 单击打开设置模块；
- 双击或明确运行按钮打开插件运行模块；
- 结束运行、禁用、卸载等操作放入上下文菜单；
- 底部放置账户占位、全局设置和必要的宿主入口；
- 在市场、插件设置和插件运行模块之间保持选择与滚动状态。

该目录是管理工作区的上下文导航，不应在 Launcher 中常驻，也不应复制成第二份插件注册表。

## 6. 分阶段开发计划

### 阶段 0：模块契约与状态机

目标：先建立无 WPF 依赖、可测试的导航内核，不改写现有业务页面。

任务：

1. 实现模块键、描述符、导航状态和会话协调器。
2. 实现打开、激活、去重、关闭、后退、前进和恢复规则。
3. 将视图关闭与插件运行停止建模为不同命令。
4. 定义作用域搜索和分离/重新嵌入契约。
5. 为旧 `ShowPage` 和 `ShowEmbeddedPlugin` 提供临时适配器。

验收：

- 纯逻辑测试覆盖模块去重、关闭回退、历史截断和根模块保护；
- 同一插件会话分离前后实例键不变；
- 无导航状态依赖 WPF `Visibility`；
- 失败创建模块不会破坏当前活动模块。

### 阶段 1：统一 Workspace Shell

目标：把现有 ToolCenter 页面迁入稳定壳层，先完成结构，不急于重做所有视觉。

任务：

1. 创建 `WorkspaceShellControl`、`ModuleStripControl`、`WorkspaceRailControl` 和 `WorkspaceContentHost`。
2. 将概览、工作流、市场、系统、诊断、开发者和设置包装为模块。
3. 建立管理中心根模块与可关闭子模块。
4. 将顶部标题区改为活动模块信息与作用域搜索区域。
5. 保留旧路由适配器，逐步移除主窗口显隐分支。

验收：

- 管理中心和市场可同时出现在模块条；
- 再次打开市场只激活，不重复创建；
- 关闭市场返回管理中心；
- 窗口缩放、主题切换和键盘焦点不丢失；
- 隐藏模块不持续运行不必要刷新。

### 阶段 2：管理中心与已安装应用目录

目标：形成截图中最关键的“管理中心也是模块”体验。

任务：

1. 将插件卡片主列表拆为稳定应用目录与插件详情模块。
2. 插件选择打开 `plugin-settings:<id>`。
3. 插件运行状态由生命周期服务统一投影。
4. 市场安装、升级、卸载完成后增量刷新应用目录。
5. 保留插件权限、热键、版本、启停、卸载和能力记录等现有管理能力。

验收：

- 在市场和插件详情间切换时，插件目录不重建、不跳顶；
- 安装完成后新插件无需重启即可出现；
- 卸载活动插件时给出明确回退；
- 插件设置页关闭不会误停后台插件；
- 25 个插件列表开启虚拟化并满足现有性能门禁。

### 阶段 3：Launcher 与 Workspace 连续性

目标：从统一入口进入管理、市场和插件时不丢任务状态。

任务：

1. 在 Launcher 提供管理中心/市场入口。
2. 插件命令需要界面时打开插件运行模块。
3. 保存调用来源、查询文本、上下文快照引用和返回路由。
4. 统一 `Esc` 层级：先关闭瞬态层，再返回模块历史，最后隐藏 Shell 并归还焦点。
5. 修正输入管线，使用户实际键入或粘贴的文本可以按命令声明传给插件。

验收：

- Launcher → 管理中心 → 市场 → 插件详情 → 返回链完整；
- Launcher → 插件运行 → 退出后恢复原查询和焦点；
- 敏感上下文仍不写入日志；
- 连续快速查询不会被旧结果覆盖；
- 键盘全流程无需坐标点击。

### 阶段 4：插件运行与分离会话

目标：嵌入、分离、重新嵌入和后台运行共享同一个插件会话。

任务：

1. 用 `PluginWorkspaceSession` 承载运行时、视图、标题、图标和状态。
2. 分离窗口接管同一视图与会话，不重复实例化运行时。
3. 明确关闭视图、返回、隐藏、后台运行和结束运行五类动作。
4. 模块条显示真实插件图标、命令来源和运行状态。
5. 延续现有每插件 AppUserModelID 和任务栏图标机制。

验收：

- 分离/重新嵌入后输入、滚动和插件状态保持；
- WebView2 不重复挂载且停止后可靠释放；
- 分离窗口任务栏身份仍为 25 / 25 唯一；
- `Esc`、关闭按钮和结束运行不会互相冒充；
- 插件崩溃只关闭对应会话，不破坏 Workspace。

### 阶段 5：市场与管理交互精修

目标：在结构稳定后完成密集、可扫描的管理体验。

任务：

1. 市场搜索迁移到顶部作用域搜索。
2. 首屏从展示型大区块调整为目录、精选、排行和详情的高效布局。
3. 市场详情作为嵌套模块或内容路由，不额外弹出无状态窗口。
4. 统一图标、加载、空状态、错误、离线、更新与确认反馈。
5. 对深浅主题、高对比度、DPI 和文本溢出重新做视觉签核。

验收：

- 720×560 最小窗口和 100%/125%/150%/200% DPI 无重叠；
- 所有按钮在亮/暗/高对比度下文字可辨；
- 列表支持键盘、屏幕阅读器与滚动位置恢复；
- 市场网络失败不阻塞本地插件管理；

## 9. 风险与控制

| 风险 | 控制措施 |
|---|---|
| 一次性重写主窗口导致回归面过大 | 先加状态机和旧路由适配器，再逐模块迁移 |
| 模块缓存导致内存回升 | 模块声明保留策略，后台刷新与视图缓存分离 |
| 插件视图被重复挂载 | 会话拥有唯一视图所有权，分离采用所有权转移 |
| 搜索作用域混乱 | 由活动模块注册作用域，Shell 统一取消旧请求 |
| 关闭语义不清 | 将关闭视图、返回、隐藏、后台和结束运行建模为不同命令 |
| 复制参考产品视觉 | 仅采纳信息架构与行为原则，视觉继续使用 Long Design System |

## 11. 当前代码结构对齐

### 11.1 工程边界

当前解决方案没有独立的 Core 或 Contracts 程序集，宿主领域逻辑、WPF UI、服务和插件引擎均位于 `LongBetterWindows.Host` 内部，并通过目录形成边界：

- `Interaction/`：无 WPF 依赖或尽量弱化 WPF 依赖的状态、协调器和投影；
- `Views/`：WPF 窗口、控件、事件转接和视图状态应用；
- `Services/`：Windows 能力、宿主级服务和插件运行协调；
- `Engine/`：插件注册、装载、Web 运行时和呈现；
- `Contracts/`：Manifest、命令调用和市场数据契约；
- `tests/LongBetterWindows.Tests/`：直接引用 Host 项目的单元、契约和架构测试。

统一工作区第一轮继续遵循该结构，不新增程序集，不移动现有公共类型，也不改动发布项目引用。待模块模型稳定、确实需要跨程序集复用时，再单独评估提取 Core 项目。
