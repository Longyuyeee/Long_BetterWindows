## 1. 执行结论

**产品方向没有发生实质偏移，主体工程已进入收口阶段，但尚未达到可直接宣布正式发布的程度。**

Long助手已经从早期的 Windows 工具集合演进为具有统一入口、上下文感知、统一工作区、
插件能力平台、可信市场与桌面 Widget 协议的 Windows 原生效率平台。当前实现符合用户后来
明确的边界：

- UI 采用 Long 自有的优雅、华丽、扁平、动效化设计语言；
- uTools 只作为统一入口、低步骤工作流、上下文匹配和插件化交互的参考；
- 不复制 uTools 视觉，不实现 uTools 插件兼容层；
- 核心能力离线优先，系统操作由宿主能力层治理；
- 插件是主要功能扩展单元，宿主负责入口、编排、权限、生命周期和统一体验。

当前可以判断为：

| 维度 | 结论 | 说明 |
|---|---|---|
| 产品定位 | 已对齐 | Windows 统一效率入口与插件平台已经形成 |
| uTools 交互参考 | 已对齐 | 搜索即行动、上下文入口、插件工作区和市场链路已落盘 |
| Long 视觉与体验 | 工程已对齐，真人签核未完成 | 主题、Token、组件、动效、DPI、辅助功能门禁已建立 |
| 插件平台 | 核心闭环已完成 | 契约、SDK、验证、打包、市场、IPC/Widget 均进入主线 |
| 发布工程 | 自动门禁通过 | 最近基线构建、测试、包与协议检查均通过 |
| 正式发布 | 未完成 | 仍有 10 类真实设备、外部环境或身份门禁 |

因此项目不应继续大规模扩张功能。下一阶段应以“重建候选、真人验证、外部分发闭环、
有限的平台债务收口”为主。

## 4. 偏移审计：哪些是偏移，哪些是合理演进

### 4.1 没有发生的实质偏移

- 没有把产品改成 uTools 兼容器；
- 没有复制 uTools Logo、品牌、具体布局或官网视觉；
- 没有放弃 Windows 原生能力、插件化和本地优先；
- 没有让功能重新散落为大量互不连通的独立窗口；
- 没有用新增插件数量代替平台质量和发布收口。

### 4.2 已确认的合理设计演进

#### 视觉：从“Apple 化”改为 Long 自有设计体系

早期文档使用了 Apple 规范、Acrylic/Mica、毛玻璃和大圆角等描述。当前实现改为石墨/紫色
语义色、克制材质、扁平层级、适量光影、自然动效和 Windows 可访问性。这不是削弱最初的
审美目标，而是把用户后来明确的“优雅、华丽、扁平、动效化”转成可维护的 Long 品牌系统。

#### 权限：从“宿主始终高权限”改为按需授权和提权

最早文档要求宿主必须以管理员模式运行。当前普通宿主默认使用用户权限，Web 插件经过能力
桥接，高风险 Native/Script 明示完全信任，只有 WPR 等确需管理员权限的任务要求单独提权。
这项变化减少了宿主被攻破后的影响范围，应视为安全修正。旧的“始终管理员运行”要求从本审计
起标记为已被取代，不应重新实现。

#### 架构：宿主“无业务逻辑”按边界原则解释

宿主现在包含搜索、工作区、市场、权限、生命周期、质量和 IPC 编排代码，因此不可能字面上
“零业务逻辑”。正确边界是：具体工具业务继续属于插件，宿主只保留平台级编排和治理。
当前符合这一原则；宿主体量持续增长仍是架构债务，需要用 SDK、Broker 和服务边界继续控制。

#### 插件形态：从简单 DLL/Web 扩展为 Native、Script、Web/Hybrid

运行时扩展是平台能力增强，不是方向变化。需要保持口径清晰：正式内置资产当前是 18 WebView
和 7 Native；Hybrid 是 WebView 插件的可选原生后台；Script 已受支持但无正式内置样本。

### 4.3 当前真实偏差与风险

1. **工程完成度与发布状态容易混淆。** 自动门禁通过不等于真人/外部验收通过。
2. **插件 UI Kit 尚未完全产品化。** 宿主已自动注入 Web UI 资产，WPF UI Kit 已有 SDK，
   但第三方版本分发、兼容矩阵与独立消费体验仍应进行一次专项收口。
3. **插件目录元数据仍有多源维护风险。** 内置 25 个、市场 Registry 8 个、示例和参考包的集合
   可以不同，但应从统一元数据生成并明确分发状态。
4. **Native/Script 仍是高信任同进程模型。** Manifest 是意图和宿主 API 边界，不是操作系统沙盒。
5. **内存门槛余量偏小。** 198.1–198.7 MB 虽然通过 `<200 MB` 门槛，但没有足够回归余量。
6. **真人批准证据仍为空。** 已存在的自动截图或诊断截图不能代替审核人、结论和证据哈希锁定。

## 6. 插件开发后续方向

### PX4：Plugin UI Kit 产品化（P1）

当前已具备宿主自动注入 `long-ui.css/js`、Long Web 组件基线和 `PluginSdk.Wpf`。后续不是
重新做一套样式，而是把现有能力变成第三方开发者可稳定消费的产品：

1. 固定 UI Kit 语义版本、兼容策略和变更日志；
2. 为 Web/Native/Script/Hybrid 样板提供统一状态、空态、错误、确认、进度和 Toast 示例；
3. 验证主题、语言、Reduced Motion、High Contrast、键盘焦点和 100%–200% DPI；
4. 增加 UI Kit 版本兼容门禁和可独立运行的预览/回归矩阵；
5. 避免第三方插件复制宿主内部资源或依赖未公开实现细节。

### PX5：目录、市场与发布者体验（P1）

现有市场安装/升级审查、发布/验证/回滚工具已经较完整，剩余重点是消除多源元数据：

1. 建立唯一插件目录元数据源；
2. 从该来源生成内置目录、市场 Registry、README/文档表格；
3. 明确 `built_in`、`marketplace`、`local_trusted`、`sample`、`reference` 状态；
4. 将 Dry Run、签名、上传、验证、部署和回滚整理为一个有审计输出的发布者流程；
5. 保持私钥和生产凭据只在受控环境，不进入仓库或普通构建产物。

### PX6：高信任运行时隔离（P2，长期）

1. 评估 Native/Script 独立进程和兼容迁移成本；
2. 引入崩溃、超时、CPU、内存和后台任务健康度；
3. 为输入注入、窗口控制、文件写入等高风险行为提供二次确认与审计；
4. 让开发工具可查看性能、错误、权限和生命周期诊断。

PX6 不阻断当前 unsigned 候选的人工验收，不应在 P0 发布门禁关闭前演变为大规模重构。

## 9. 收口判定标准

只有同时满足以下条件，才能把项目从“工程接近收口”改为“候选可发布”：

- 干净提交的 Release 构建、全量测试、插件矩阵、LPWP 和包审计全部通过；
- 25 / 25 插件具有有效人工批准回执；
- 10 类真实人工/外部门禁全部通过或有经过书面批准的明确延期决策；
- 所有批准证据与最终候选提交和包哈希一致；
- GitHub CI 对最终提交通过；
- 安装、升级、卸载、更新与回滚路径均有真实环境证据；
- 最终收口报告明确输出 `release_eligible=true`；
- Prerelease 标签、Release 资产和发布说明与最终候选完全一致。

在此之前，准确表述应为：**Long助手主体设计与工程目标已经对齐，代码已进入发布前人工/外部
验收阶段；尚未完全收口，也尚未获得正式发布资格。**
