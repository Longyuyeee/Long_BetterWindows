# 插件人工证据验收

本文用于关闭 `docs/plugin-positive-function-matrix.json` 中 25 项真实桌面人工检查。自动测试、隔离宿主和机器探针不能代替人工确认；未经实际操作和逐份审阅，不得生成批准回执。

## 证据模型

- 原始截图、录像和机器报告保存在 `artifacts/quality/`，不提交 GitHub。
- 仓库只提交 `docs/plugin-manual-approvals/` 下的批准回执。
- 回执记录审阅人、说明、源码提交、插件 Manifest 哈希、受测 Release EXE 哈希、命令集合，以及每份原始证据的相对路径、大小和 SHA-256。
- 校验器不要求其他电脑持有原始大文件，但会复核回执的来源、范围和哈希元数据。
- 批准后只要 `src/` 发生变化、Manifest 或命令集合变化，旧回执即失效，必须重新验收。

## 先锁定候选与下一项

不要从开发构建目录挑选 EXE，也不要手工抄写下一项。RC 候选生成后，在干净跟踪工作区运行：

```powershell
.\plan-next-plugin-validation.ps1 `
  -OutputPath "artifacts/quality/plugin-manual-session/next.json"
```

规划器会同时验证：

- 当前版本与 `artifacts/releases/v<版本>/release-manifest.json` 一致；
- Release Manifest 来自干净、可打包的候选提交，且该提交是当前 `HEAD` 的祖先；
- 候选之后只允许增加 `docs/plugin-manual-approvals/*.json` 回执，源码、脚本或普通文档变化会判定候选过期；
- 自包含 ZIP 的 SHA-256 与 Manifest 一致，解压目录中的受测 EXE 与 ZIP 内 EXE 逐字节哈希一致；
- 插件矩阵和已有回执合同有效。

输出中的 `next` 按 `low → medium → high → critical` 和矩阵原始顺序选出下一项，包含插件 ID、检查 ID、
命令、英文验收描述、建议证据目录、冻结 EXE 哈希和可复制的批准命令模板。使用
`-PluginId "com.long.base64"` 可只定位指定插件。`next=null` 且 `complete=true` 才表示 25 项都已有有效回执。

规划器不会启动软件、采集证据或生成通过回执，也不会把人工观察自动标记为通过。

确认计划后，推荐使用一键会话入口：

```powershell
.\start-plugin-validation.ps1
```

入口会再次执行全部规划校验，拒绝已有 Long助手宿主进程，创建该检查独占的证据目录和
`validation-session.json`，再从正确工作目录启动冻结 EXE。会话文件记录候选提交、插件/检查 ID、命令、
受测 EXE 哈希、启动时间和进程 ID，状态固定为 `pending_human_observation`。它不会截图、点击界面或批准检查。

只准备目录而不启动软件时使用 `-PrepareOnly`；之后不带该参数再次运行，会且只会恢复候选、插件、检查和 EXE
哈希完全一致的 `prepared_only` 会话，并在启动前原子改为 `launching`，避免并发重复启动。定位特定插件时使用
`-PluginId`。其他已有目录一律拒绝；重试时通过 `-EvidenceDirectory` 指定新的 `artifacts/quality/` 子目录。

## 执行步骤

1. 使用一键会话入口启动冻结 RC；不得改用后续重新构建的 EXE。

   ```powershell
   .\start-plugin-validation.ps1
   ```

2. 按 [插件正向功能验收矩阵](插件正向功能验收矩阵_2026-07-27.md) 操作对应插件。高副作用检查只能使用可丢弃文件、临时监听进程和无害目标应用。
3. 将原始证据保存到本次专用目录，例如：

   ```text
   artifacts/quality/plugin-manual-9b6152f/
   ```

4. 逐份检查原图、录像和报告后，复制规划器给出的 `approval_command`，补齐真实审核人与证据路径后创建回执。示例：

   ```powershell
   .\approve-plugin-manual-evidence.ps1 `
     -PluginId "com.long.window-manager" `
     -ManualCheckId "layouts-topmost-multimonitor" `
     -Reviewer "实际审阅人" `
     -Notes "已验证正常/最小化/最大化窗口、多显示器、置顶和高权限拒绝。" `
     -EvidenceFiles @(
       "artifacts/quality/plugin-manual-9b6152f/window-manager-report.json",
       "artifacts/quality/plugin-manual-9b6152f/window-manager-layout.png"
     ) `
     -SubjectExecutable "artifacts/releases/v1.11.0-rc.3/self-contained/LongBetterWindows.Host.exe" `
     -ConfirmPassed
   ```

5. 检查生成的 JSON，只暂存批准回执，不暂存 `artifacts/`。提交该回执后重新运行规划器，它会给出下一项。
6. 运行聚合校验：

   ```powershell
   .\verify-plugin-positive-matrix.ps1 `
     -OutputPath "artifacts/quality/plugin-positive-matrix/report.json"
   ```

7. 仅当 25 项人工检查都存在有效回执，且跟踪工作区干净时，运行发布门禁：

   ```powershell
   .\verify-plugin-positive-matrix.ps1 -RequireReleaseEligible
   ```

## 修改与撤销

- 首次批准不得使用 `-Replace`；重新完整验收同一项且旧回执存在时才可使用 `-Replace`。
- 首次回执不可覆盖且原子创建；重审会锁定旧回执 SHA-256 并原子替换。目标变化或另一审核进程先提交时，本次重审会失败，不得通过再次并发运行覆盖其结论。
- 如果检查失败或证据不足，不生成回执，在审计文档中记录问题和复现条件。
- 发现误批时删除对应回执并提交该删除；原始证据仍按本地质量资料保留。
- 不要手工将矩阵基础状态改成 `passed`。校验器会把有效回执投影为当前提交的有效通过状态。

## 与其他人工门禁的边界

本流程只处理插件正向功能矩阵的 25 项检查。任务栏肉眼分组、物理 DPI、辅助功能/Narrator 和管理员 WPR 使用各自的采集与批准脚本，不能用插件回执替代。
