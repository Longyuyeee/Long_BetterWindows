# Long助手严重问题审计与整改计划

> 审计日期：2026-07-27
> 审计起点：`master` / `origin/master` @ `26b5732`（`v1.11.0-rc.2`）
> 范围：主题与颜色、交互性能、25 个内置插件、分离窗口任务栏身份
> 发布判断：`v1.11.0-rc.2` 被真实用户测试阻断，不再作为可发布候选

## 1. 结论

用户报告的四类问题均能在代码或真实运行中找到依据，不是单纯的环境差异：

1. 运行时主题切换只更新颜色资源，没有替换既有画刷实例，造成主体切换而标题栏、控件仍保持旧主题。基础按钮悬停模板还会把主按钮背景改成普通表面色，但保留白色前景。
2. QuickLaunch 在每次输入时同步递归扫描文件和文件内容；本地文件索引还会频繁复制大列表并对完整索引排序。这是交互卡顿的高可信根因。
3. Web 插件初始化在导航和 JS 命令处理器就绪前返回，真实命令存在随机失败或 30 秒超时。DevToolkit 没有命令处理器，PortManager 调用了不存在的桥接方法，WindowManager 指南依赖跨程序集窗口样式并在运行时解析失败。
4. 分离插件窗口沿用宿主进程身份和图标，并设置主窗口为原生 Owner，Windows 任务栏会将其继续视为同一应用。

本轮先修复共性根因和已复现插件故障。候选恢复前仍需完成 5 个高副作用/外部依赖插件的人工功能验收，以及真实任务栏分组观察。

## 2. 已完成整改

- 主题切换现在重新生成语义画刷和兼容别名，不再只替换 `Color`。

- 真实 UI Automation 验证暗色切换亮色后，主体和标题栏同步更新。

### 2.2 性能

- QuickLaunch 搜索增加取消、180 ms 防抖和查询版本校验。
- 文件名及内容递归扫描移到后台线程；窗口关闭时取消未完成搜索。

- 空闲测量没有发现持续 CPU 异常；当前高优先级问题集中在交互式磁盘扫描。

### 2.4 分离窗口任务栏身份

- 分离窗口不再设置主窗口为原生 Owner，只保留应用内返回目标。
- 每个插件使用稳定的 `LongAssistant.Plugin.<plugin-id>` AppUserModelID。
- 每个插件生成确定性独立图标，并在窗口句柄创建后写入任务栏身份。
- 代码与命令冒烟已确认属性写入不再抛异常；最终分组效果仍需在真实任务栏人工确认。

## 8. 第三轮性能与启动状态审计

2026-07-27 继续针对“软件运行后电脑卡顿”审计启动链路和 QuickLaunch：

1. 确认统一命令执行器此前会把按需启动等同于用户启用，并在每次首次调用插件时持久写入 `auto_start=true`。插件一旦被命令中心或工作流使用，后续启动便可能永久增加自动启动项。现已为 `PluginRegistry.StartPluginAsync` 增加明确的持久化参数；插件管理页主动启用仍会保存设置，命令执行仅在本次会话启动插件，不再改变下次启动策略。

## 21. 第十六轮注册批处理与 WPF 线程归因

本轮首先修复插件目录扫描的通知边界。此前每个插件的延迟注册、语言投影和状态变化都会立即触发全局 `PluginsChanged`，插件页、概览、命令中心和其他已加载订阅者分别响应。现在 `PluginRegistry.BeginChangeBatch()` 提供可嵌套事务，扫描器在目录插件注册批次外层使用；注册和自动启动仍逐项完成，批次结束只发布一次稳定目录快照。

自动化契约覆盖多次变更合并、嵌套提交、空批次不发布以及重复 Dispose 安全。该整改与最初设计中的“稳定插件目录投影、注册中心统一发布”边界一致，没有把批处理逻辑散落到各页面。

质量探针同时修正测量口径：

- `plugin_runtime_ready` 记录扫描和运行时完成时刻。
- `plugin_page_settled` 等待页面 150 ms 去抖及 Dispatcher ContextIdle，确认最终 25 项已经投影。
- 1/3/9 秒检查点从稳定页面开始，避免把最终容器实现误算为空闲增长。
- 每个样本记录 CPU 最高的五个原生线程，报告记录 WPF UI 原生线程 ID。

三轮稳定节点样本：

- 运行时就绪时列表均为 0 项，340.3–389.0 ms 后稳定为 25 项。
- 稳定过程消耗 187.5–250.0 ms CPU，完整投影均为初始和最终两次。
- 上一轮页面去抖后已经是两次投影，因此注册批处理只认定减少全局通知和其他订阅者重复工作，不宣称插件页本身进一步变快。

线程归因：

- 稳定可见样本在 3–9 秒只增加 46.9 ms CPU。
- 异常可见样本增加 1703.2 ms，其中 WPF UI 线程增加 1046.8 ms，另一高占用线程增加 562.4 ms。
- 隐藏样本增加 78.1 ms，UI 线程只增加 62.4 ms。
- 另外两轮隐藏窗口在 3–9 秒分别只增加 46.9 ms、31.3 ms，托管堆固定 10.2 MB、GC 提交量固定 15.8 MB。

审计结论：

1. 自动启动插件、文件监控、计划任务和托管泄漏不再作为间歇性长尾主方向。
2. 剩余长尾位于可见 WPF Dispatcher/渲染链，但并非每轮必现；插件页没有被使用的无限动画，列表已启用 Recycling 虚拟化，卡片阴影已关闭。
3. 当前机器未安装 `dotnet-trace`、WPR/WPA。下一步必须在具备 ETW 或 Visual Studio Profiler 的环境捕获异常轮次 UI/渲染线程调用栈，再修改具体高占用方法，不做猜测性视觉降级。
4. 性能 P0、严格 `<200 MB` 工作集门槛、新 RC、主题/任务栏和高副作用插件人工验收继续阻断。
5. 原始报告和 `audit-summary.json` 位于 `artifacts/quality/registry-batch-20260727/`。

## 23. 第十八轮分离窗口任务栏身份闭环

本轮复审发现原有 AppUserModelID 只把非字母数字字符替换为句点，因此 `plugin-a` 与 `plugin_a` 会归一化为同一身份；写入 Shell 属性失败时也没有可观测结果。原静态测试只比较两个普通 ID，无法证明真实窗口句柄已经收到属性。

整改：

1. AppUserModelID 由可读归一化前缀和原始插件 ID 的 12 位 SHA-256 摘要组成。摘要按插件注册表一致的不区分大小写语义计算，归一化碰撞不再导致任务栏身份碰撞。
2. ID 总长限制为 Windows 允许的 128 字符；超长插件 ID 保留前缀并截断可读部分，不截断摘要。

## 29. 第二十四轮截图与取色物理屏幕链路收口

本轮沿 Screenshot 与 ColorPicker 的正向链路逐层审计，确认原实现存在四项实际风险：Screenshot 插件和宿主各维护一套 GDI 截图；全屏和区域截图把 WPF 逻辑坐标直接传给物理屏幕 API；区域截图在遮罩窗口关闭前执行，会把半透明遮罩截入结果；宿主 GDI 路径不检查句柄、`SelectObject` 和 `BitBlt` 结果，失败时也不能保证按正确顺序恢复和释放对象。ColorPicker 还使用当前窗口 DPI 手工换算另一显示器的鼠标坐标，复制回调抛错时窗口无法稳定关闭。

整改：

- Screenshot 插件删除私有 GDI 实现，统一调用宿主 `IScreenCaptureService`；全屏位图、区域位图和 Web 截图能力共享同一实现。
- 宿主使用 `GetSystemMetrics(SM_*VIRTUALSCREEN)` 获取物理虚拟屏幕，区域参数必须为正且完全位于虚拟屏幕内，避免越界和异常尺寸进入 GDI。
- GDI 路径检查 `GetDC`、兼容 DC/位图、`SelectObject`、`BitBlt`，加入 `CAPTUREBLT` 捕获分层窗口；位图跨线程前冻结，并在 `finally` 中恢复旧对象后释放所有句柄。
- `CaptureFullScreenAsync` 通过注入的 `IClipboardService` 写入，不再直接调用 WPF 全局 Clipboard，也不再依赖 UI Dispatcher 执行 GDI。
- 区域选择器用 `GetCursorPos` 记录拖拽起止物理坐标；选区完成后先关闭遮罩并等待 Dispatcher 空闲，再调用宿主截图，避免遮罩污染结果。
- 新增宿主 `ScreenColorSampler`，集中管理 `GetDC/GetPixel/ReleaseDC`。ColorPicker 使用真实物理光标坐标采样，并复用 `MonitorHelper.GetCursorPlacement` 放置跨屏浮窗。
- ColorPicker 的选择回调使用 `finally` 关闭窗口，剪贴板或提示链路异常不再残留捕获循环和浮窗。

验证：

- 当前 Windows 会话直接执行宿主全虚拟屏幕捕获，返回位图尺寸与物理虚拟屏幕一致、位图已冻结；通过记录型剪贴板验证服务交付对象和尺寸一致，测试不覆盖用户当前系统剪贴板。
- 当前 Windows 会话直接采样虚拟屏幕中心物理像素，返回有效不透明 RGB；无 UI 合成点击或坐标模拟。

## 30. 第二十五轮 FolderNote ADS 事务与失败恢复收口

## 33. Macro 可等待取消与异常清理闭环

本轮没有执行真实全局 Hook 或向用户桌面发送键鼠输入，而是先把原生边界改为可注入接口，再用故障注入覆盖高风险时序。原实现的根因是播放只持有取消源，循环停止和插件停止不等待 `_playTask`；鼠标/键盘按下与抬起之间的可取消延迟没有 `finally` 释放；`keybd_event` 无返回结果；循环后台任务异常只能留在未等待任务中。

整改：

1. 新增 `IMacroNativeApi`，统一 Hook 安装/卸载、Hook 数据、光标与鼠标/键盘 `SendInput`。所有原生变更检查返回值和 Win32 错误，键盘不再使用不可验证的 `keybd_event`。
2. 单次与循环播放共用任务、取消源和启动门。`StopPlayAsync` 等待任务完成；插件停止在注销热键后等待播放、Hook 和待释放输入全部清理，失败则进入 `Error` 并返回 false，不提前声称停止。
3. 成功发送按下事件后立即登记待释放键或鼠标按钮。正常抬起移除登记；取消和任何异常都在 `finally` 中补发抬起，每项最多重试 3 次。仍失败的登记不会丢失，后续停止或异步释放继续重试。
4. 鼠标释放保留原操作坐标，不会因错误清理把光标移动到虚拟桌面左上角。循环异常被任务内部观察并通过 `PlaybackFailed` 反馈；状态事件订阅者异常被隔离。
5. Hook 部分安装失败会清理已安装句柄；清理失败进入 `Faulted` 并保留失败句柄供再次停止。Overlay 关闭同步停止计时器和动画，避免关闭后的 UI 生命周期残留。

验证：

- 鼠标按下后取消：停止等待完成并发送匹配坐标的 MouseUp。
- 键盘按下后取消：停止等待完成并发送对应 KeyUp。
- KeyUp 原生失败：`finally` 重试释放；连续 3 次失败返回结构化失败并由释放阶段再次重试。
- 循环播放：停止等待后台延迟和释放完成后才回到 Idle。
- 输入原生失败：后台异常被观察、发布失败事件并恢复 Idle。
- Hook：覆盖第二个 Hook 安装失败、已安装 Hook 清理、卸载失败进入 Faulted 和再次停止恢复。
- 状态观察者抛出异常不会破坏输入释放或 Idle 收尾。
- 定向门禁 10 / 10 通过；Release 构建 0 警告、0 错误；全量自动化 736 / 736 通过。

审计结论与下一步：

## 38. QuickLaunch 大目录响应、过期结果与启动边界

整改：

4. 新增单调 `QuickLaunchQueryGeneration`。每次查询获得新代际，后台结果发布必须同时满足令牌未取消、代际仍为最新和文本仍一致；窗口关闭会主动失效代际。
5. 新增 `QuickLaunchTargetPolicy`。应用目标必须是开始菜单根内现有 `.lnk`，普通文件必须存在且不是重解析点，链接只允许 HTTP(S)，计算结果限制长度，未知分类固定拒绝。

## 39. ColorPicker / Screenshot Overlay 生命周期与晚到交付

## 41. WindowManager / Macro 停止事务与残留回调

本轮继续第 40 节后的关键级桌面插件收口。自动化只使用内存热键服务、隔离窗口 Native API 和宏 Native API 假实现，不操作用户窗口、不注入输入、不安装真实全局 Hook；真实正向体验仍保留人工签核。

审计发现：

1. WindowManager 与 Macro 的 `StopAsync` 无条件清空 `_registeredHotkeys`，忽略每次 `UnregisterAsync` 的响应，并固定返回成功。
2. 当 Windows 注销热键失败时，宿主可能据此继续卸载插件，而全局热键仍引用旧插件回调；插件本身也丢失失败热键，无法在第二次停止时重试。
3. Macro 使用不带插件 ID 的注册重载，所有权依赖宿主从调用栈推断；这与正式插件身份和停止事务的确定性要求不一致。
4. Macro 在任一停止失败路径上需要同时处理两类资源：全局热键与宏引擎。热键失败不能成为跳过 Hook、播放任务和已按下输入清理的理由。
5. WindowManager 停止路径直接访问 `Application.Current.Dispatcher`，在隔离生命周期验证或无 WPF Application 的安全宿主中会空引用，妨碍机器闭环。

整改：

1. 两插件改为对热键登记快照逐项注销，只从列表删除成功项；失败项保留原所有权和回调登记，汇总错误后进入 `PluginState.Error` 并返回 `false`。
2. 第二次停止只重试仍在列表中的失败项；全部注销后进入 `Stopped`，从而为暂时性 Win32 注销失败提供确定恢复路径。
3. Macro 的首选和回退热键注册显式传入 `com.long.macro`，不再依赖调用栈身份推断。
4. Macro 无论热键注销是否失败都继续调用引擎 `StopAsync`。引擎成功后解除状态/失败事件并释放实例；引擎失败则保留实例供重试，Overlay 仅在引擎安全停止后关闭。
5. WindowManager 关闭指南前检查 WPF Application 是否存在，隔离宿主可验证完整停止事务。
6. WindowManager 与 Macro 分别升至 `2.1.2`、`1.1.2`；源码 Manifest、运行时投影和文档注册表同步。
7. 新增 `verify-desktop-side-effect-lifecycle.ps1`，绑定 9 个 MacroEngine 故障/取消案例和 2 个插件停止恢复案例；证据记录测试程序集 SHA-256、Git 提交和工作区状态。

- Macro 注册 3 个显式所有权热键后注入一次注销失败：首次停止仍完成引擎清理并只保留失败热键；第二次停止成功且登记归零。

- Release 构建 0 警告、0 错误；全量自动化 762 / 762。

结论与后续：
