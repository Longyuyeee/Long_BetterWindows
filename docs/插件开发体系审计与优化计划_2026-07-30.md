# Long助手插件开发体系审计与优化计划

> 审计日期：2026-07-30
> 审计基线：`agent/window-manager-transactional` / `7f415dad1a0c038cd811cabea182045990f5df75`
> 产品原则：参考 uTools 的统一入口、上下文匹配和插件化交互逻辑，不实现 uTools 插件兼容层

## 1. 审计结论

插件运行平台、25 个内置插件、可信市场、命令契约、权限声明、生命周期、双语资源和发布门禁已经形成完整工程闭环。当前阶段不应继续以增加插件数量为优先目标，而应收口开发者体验、契约单一来源、UI Kit、打包验证和分发目录。

“完全落盘”需要区分三个层级：

1. 当前受跟踪源码已经提交，并通过 17 个提交的纯快进整合进入 `master`。
2. Draft PR #12 作为整合来源保留；后续开发直接以 `master` 为正式基线。
3. 本地 `artifacts/**` 原始截图和质量报告按策略不提交；人工批准回执、物理设备和外部分发门禁尚未完成，因此不能宣称正式发布收口。

## 3. 已对齐能力

### 3.1 运行时

宿主真实支持三种运行时：

| Manifest `runtime` | 入口 | 信任边界 |
|---|---|---|
| 缺省 / `native` | `.dll` | 本地完全信任 |
| `csharp-script` | `.csx` | 本地完全信任 |
| `webview` | `.html` | 能力声明、页面来源和桥接协议约束 |

WebView Manifest 还可声明 `background.entry_point`，将按需 Web UI 与实现 `ILongPlugin` 的原生后台组件纳入同一生命周期。

### 3.2 插件契约

当前 Manifest 已覆盖：

- ID、版本、作者、入口、运行时和最低兼容版本；
- 权限能力、依赖、默认设置；
- 统一命令、输入类型、结构化参数 Schema、预设与输出声明；
- 窗口模式、建议尺寸和生命周期；
- 本地化资源；
- Web UI 原生后台组件。

宿主已经具备 Manifest 静态验证、包结构验证、依赖解析、运行时加载、热更新监控、资源释放、命令执行、设置投影、任务栏身份和市场事务能力。

### 3.3 质量与发布

25 个插件已经进入唯一正向功能矩阵。低、中、高风险命令均具有不同程度的隔离真实宿主执行证据；关键桌面副作用继续保留人工签核。市场具备签名校验、安装、升级、降级、卸载、中断恢复、离线缓存、并发控制、发布、验证和回滚链路。

## 4. 当前缺口

### P0：契约和文档存在多源漂移

- 当前权威文档应为 `docs/插件开发指南.md`，但 README 文档导航和用户指南仍可能把开发者引向历史 `docs/DEVELOPER_GUIDE.md`。
- 历史文档使用过 `entry`、`dotnet` 和旧能力名称；真实契约使用 `entry_point`、缺省/`native`、`storage.local` 等。
- 能力清单、Manifest 字段、API 文档和模板主要靠人工同步，仍可能再次漂移。

### P0：脚手架入口不一致

- `src/Templates/script-plugin` 已存在，权威开发指南也使用 `-Template script`，但本次审计基线上的 `new-plugin.ps1` 参数校验仍拒绝 `script`。
- 命令行脚手架以原生模板为主，应用内开发工具以 Web/Script 为主，两边没有共享模板目录和生成契约。
- 原生脚手架直接使用由插件 ID 转换出的带连字符目录名作为 C# 标识符，可能生成非法项目/类型名称。

### P0：打包器未复用生产验证链

`pack-plugin.ps1` 当前主要读取基本字段并压缩目录，尚未完整复用 `ManifestReader` 和 `PluginPackageValidator` 的生产规则。开发者可能在打包成功后，才在安装阶段发现入口、能力、兼容版本或包结构错误。

### P1：缺少版本化开发 SDK

- Web 插件没有独立发布的 TypeScript 类型声明和 Mock Host。
- 原生插件需要直接依赖宿主程序集路径，缺少稳定的 Contracts SDK/NuGet 边界。
- 缺少统一的插件测试宿主、命令契约测试模板和 CI 模板。

### P1：插件 UI Kit 尚未产品化

Manifest 已有 `min_ui_kit_version`，但插件开发者仍缺少可版本化引用的 Long UI Kit。内置插件虽然已经使用统一视觉原则，第三方 Web 插件仍容易形成不一致的颜色、间距、动效、焦点、空状态和错误状态。

### P1：插件目录口径分散

正式内置插件为 25 个，宿主市场目录为 8 个，文档示例 Registry 为另一套集合。集合可以不同，但应由同一元数据源生成并显式标注 `built_in`、`marketplace`、`local_trusted`、`sample` 等分发状态。

### P2：高信任插件缺少进程级隔离

Web 插件已有桥接能力边界；DLL 和 C# Script 仍可直接使用 .NET、P/Invoke 和文件系统。Manifest 权限只表达宿主 API 使用意图，不是操作系统沙盒。中长期应评估独立进程、崩溃隔离、资源预算和高风险能力二次授权。

## 5. 分阶段开发计划

### PX1：契约单一来源与脚手架闭环

目标：

1. 明确 `docs/插件开发指南.md` 为唯一当前开发指南，历史指南增加醒目标记并从 README 主导航移除。
2. 修复 `new-plugin.ps1 -Template script`，并保证脚本模板替换 ID、名称、作者和热键后可直接被宿主发现。
3. 修复原生模板的合法 C# 项目名、类型名和命名空间生成。
4. 增加质量门禁，防止权威指南、脚手架和模板再次漂移。
5. 设计机器可读 Manifest JSON Schema 的字段与生成位置。

完成标准：

- 指南中的三种运行时创建命令均与真实脚本一致；
- C# Script 创建后具备有效 `runtime`、`entry_point` 和入口文件；
- 原生模板生成的项目可构建；
- 定向测试、全量测试和 Release 构建通过。

### PX2：生产级插件验证与打包

目标：

1. 提供独立 `validate-plugin` 入口，复用生产 Manifest 和包验证规则。
2. `pack-plugin.ps1` 在创建 `.lpak` 前执行入口、运行时、能力、依赖、兼容版本和安全路径验证。
3. 包内生成确定性文件清单与 SHA-256；禁止临时文件、构建缓存和秘密文件进入包。
4. 输出本地高信任/远程市场分发资格和权限摘要。

完成标准：

- Web、Script、Native、Hybrid 四种样板均有成功案例；
- 非法入口、路径穿越、未知能力、缺失依赖和不兼容版本均在打包前失败；
- 生成包可由生产安装验证器接受。

### PX3：开发 SDK 与测试宿主

目标：

1. 发布 TypeScript `long.*` 类型声明、事件模型和 Mock Host。
2. 拆出稳定的 .NET Contracts SDK，消除插件对宿主构建目录的直接引用。
3. 提供插件命令、生命周期、权限拒绝、语言切换和资源释放的测试模板。
4. 为三种运行时提供最小 CI 示例。

完成标准：

- 示例插件可在不启动完整 WPF 宿主时运行契约测试；
- SDK 版本与 Manifest `min_api_version` 可验证；
- 示例和内置插件不再复制宿主接口定义。

## 7. 发布与人工门禁关系

插件开发体验优化不改变现有发布阻断：

- 25 项真实桌面插件操作仍需用户逐项批准；
- 任务栏分组、四档物理 DPI、辅助功能/读屏、管理员 WPR/WPA 仍需真实环境；
- 真实下载、干净 Windows、Registry/CDN 发布与回滚仍属于外部门禁；
- 只有冻结提交重新构建候选并通过最终聚合决策后，才可声明正式发布。

开发体验批次可以与人工验收准备并行推进，但不得自动把人工状态从 `pending` 改为 `passed`。
