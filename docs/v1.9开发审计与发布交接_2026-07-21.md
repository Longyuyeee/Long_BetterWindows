> 审计日期：2026-07-21

> 审计范围：产品目标、UI/UX、插件平台、可信市场、发布工具、自动化证据和外部发布条件

## 1. 执行结论

当前开发方向与最初目标保持一致，v1.9 的产品功能和代码侧发布门禁已基本收口，可以进入“外部发布条件执行”阶段，但**尚不能标记为正式 Release**。

核心结论如下：

1. 产品定位已经从工具集合收敛为 Windows 本地效率中枢：统一命令中心、上下文匹配、超级面板、插件生命周期和可信市场形成完整主链路。
2. 对 uTools 的参考边界符合既定决策：参考统一入口、搜索匹配、插件化和低打扰交互逻辑；不实施 uTools 插件兼容层，不复制其品牌或视觉资产。
3. UI 已对齐“优雅、华丽、扁平化、动效化”的内部 Long Design System，并补齐核心窗口的键盘路径、UI Automation 名称、控件类型和动态状态语义。
4. 可信插件市场已从界面状态直连重构为独立会话协调器，覆盖加载取消、操作防重入、确认态、失败保留、成功清理和刷新。
5. 本地发布、市场签名部署/回滚、辅助功能、干净 Windows 环境和 Authenticode 签名均已建立可阻断的工具链。
6. 已从干净提交 `11c22b2` 重建双候选，Manifest 为 `source_dirty=false`；`signed=false`、`release_eligible=false` 仍如实保留，必须由正式 Authenticode 流程推进，不得手工修改 JSON 绕过。

综合判断：

- **产品目标对齐度：高**
- **代码功能完成度：高**
- **自动化质量状态：通过**
- **正式发布准备度：有条件未通过**
- **当前主要风险：外部证书、真实设备、真实分发环境和人工签核，而非核心功能缺失**

## 3. 产品目标对齐审计

### 3.1 统一入口与交互逻辑

已完成：

- 全局命令中心承担统一搜索、命令执行、插件进入和输入路由。
- 超级面板提供上下文结果、分组、固定项、拖拽、二级动作和命令中心跳转。
- 托盘、全局热键、主窗口、命令中心和插件窗口之间具有明确的进入与返回路径。
- 上下文 Provider、静态命令和插件命令共享统一搜索与执行协议。

与参考产品的关系：交互理念对齐，但保持 Windows 原生、本地优先和 Long 自有设计语言，不建立 uTools 二进制或插件 API 兼容性。

### 3.2 插件平台

已完成：

- 支持 DLL、C# Script、WebView2 三类运行时。
- 25 个内置插件均具有唯一 ID、命令、窗口和生命周期声明。
- 27 个宿主能力接口继续作为插件能力边界。
- Web 插件具有桥接协议、权限校验、导航限制、下载限制和资源释放路径。
- 插件扫描、运行时装载、热重载和 WebView2 呈现已从大型宿主类拆分。

当前没有继续增加插件数量，因为 v1.9 的优先级是发布可信度和体验签核，而不是扩大工具清单。

### 3.3 可信插件市场

已完成：

- 远程 Registry、发布者信任、公钥签名、SHA-256、兼容性和权限差异检查。
- 安装、升级、降级、卸载、中断恢复和离线可信目录回退。
- 网络重试、超时、同包并发合并、陈旧分片清理。
- `MarketplaceSessionCoordinator` 统一管理目录加载取消、远程/本地包准备、确认态和操作防重入。
- 本地覆盖部署会保留不可变历史包与 Release 恢复点，Registry 回滚后旧包仍可下载。
- 生产演练在部署前强制候选 Dry Run、Registry 最后提交检查和现网公开基线验证，并支持无上传凭据的只读预检。

### 3.4 UI/UX 与可访问性

已完成：

- 主要窗口、搜索框、结果列表、市场操作、插件管理和通知使用 Long Design System。
- 核心 Window/Edit/List/Button 已补充 UI Automation 名称、类型和焦点能力验证。
- 动态状态使用 Live Region，键盘执行、菜单、Escape 返回、窗口切换和插件分离返回已进入桌面冒烟。
- 工程渲染矩阵覆盖亮/暗主题、96/120/144/192 DPI 和三类可访问性模式。
- 建立物理 DPI、真实辅助功能、干净 Windows 生命周期的“采集—人工批准—汇总”三段式门禁。

仍需注意：工程渲染不能替代真实显示器、Windows 系统设置和屏幕阅读器人工观察。

## 4. 本批次主要工程变化

### 4.1 市场会话收口

- 新增 `MarketplaceSessionCoordinator`，界面不再保存包路径、卸载 ID、Metadata 和 Validation 等事务状态。
- 新目录请求会取消旧请求；重复准备和重复确认会被拒绝。
- 安装失败保留可重试确认态，成功后清理状态并刷新列表。
- 增加纯逻辑协调器测试和真实隔离市场事务证据。

### 4.2 市场发布与回滚

- 本地覆盖部署保留 `packages/` 和 `releases/` 历史内容。
- 遇到同路径不同内容、重解析点或越界路径时拒绝部署。
- 新增一次性 RSA 本地演练，覆盖基线、候选 Dry Run、覆盖、回滚和私钥删除。
- 生产演练器增加只读 `PreflightOnly`，并确保候选和现网基线验证早于任何 Registry 写入。

### 4.3 发布包门禁

- 发布脚本验证 25 个插件目录、25 个 Manifest、25 个唯一 ID 和 42 条命令。
- 两种包均执行真实 Base64 命令，并记录退出码和 WebView2 进程差集。
- Manifest 记录提交、源码是否脏、包哈希、包体积、插件/命令数量与 Release 资格。

### 4.4 真实环境证据链

- 辅助功能门禁读取真实 Windows 高对比度和动画设置，并可确认 Narrator/NVDA 进程。
- 干净 Windows 门禁直接解压候选 ZIP 运行桌面 UI/WebView2 冒烟，并要求另一审核人确认首启、托盘、热键、升级、回滚和卸载。
- Authenticode 流水线只从 Windows 证书存储区调用私钥，不接受 PFX 口令参数；签名采用 SHA-256 和 RFC 3161 时间戳。
- 签名输出不会覆盖输入目录，成功前只存在临时目录；独立验证器会重新解压用户下载 ZIP 并逐个验证产品 PE 文件。

## 6. 尚未完成的发布条件

### P0：正式发布前必须完成

1. [x] **冻结源码候选**：已从干净提交 `11c22b2` 执行 `release.ps1`，双候选 Manifest 记录 `source_dirty=false`，实际 ZIP 哈希与 Manifest、SHA256SUMS 一致。
2. **正式代码签名**：本机已有 Windows SDK SignTool，但 `CurrentUser\My` 中没有带私钥的 Code Signing 证书。签名与独立复验现已强制核对完整 40 位源码提交，候选顶层提交与签名元数据任一不一致都会阻断；接入正式证书后再执行签名、打包和独立复验。
3. **真实 Registry/CDN**：使用正式公钥、HTTPS 端点和受控上传凭据完成预检、部署、验证、回滚；凭据不得进入仓库。
4. **干净 Windows 生命周期**：在新用户或一次性虚拟机完成首次启动、托盘、热键、WebView2、升级、数据保留、回滚和卸载清理，并由独立审核人批准。
5. **SmartScreen/杀毒软件**：记录真实下载、解压和启动结果。代码签名不等同于已有 SmartScreen 信誉。

### P1：正式体验签核

1. 在物理 100%、125%、150%、200% DPI 显示环境完成亮/暗主题人工批准。
2. 在真实高对比度、关闭动画和组合设置下完成键盘、焦点和动画检查。
3. 至少一个配置使用 Narrator 或 NVDA 完成动态状态朗读确认。

## 7. 风险与控制

| 风险 | 当前控制 | 剩余动作 |
|---|---|---|
| 把脏源码候选当正式包 | Manifest 固定 `source_dirty`，签名脚本直接拒绝 | 已从 `11c22b2` 干净重建；签名前复核 |
| 伪造或误签旧候选 | 强制核对完整源码提交，独立解压 ZIP 并校验证书指纹、时间戳和文件数 | 接入正式证书执行 |
| Registry 更新后旧包丢失 | 保留历史 packages/releases，回滚测试验证旧引用 | 真实 CDN 演练 |
| 市场重复点击/加载竞态 | 会话协调器取消、防重入和确认态管理 | 继续监测真实网络 |
| 工程截图冒充物理设备 | 证据分类明确，人工批准与哈希锁定 | 完成四档物理 DPI |
| 自动可访问性冒充真实读屏 | 真实系统设置和读屏进程检测，至少一次朗读签核 | Narrator/NVDA 人工执行 |
| 临时证据污染仓库 | 本次仅提交源码、脚本和正式文档 | 后续完善 artifacts 忽略策略 |
