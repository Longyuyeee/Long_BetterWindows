## 1. 已确认的发布决策

### 1.1 最终版本是稳定版

本轮目标不是再停留在公开 RC，而是最终发布 `v1.11.0` 稳定版。为避免把 RC 二进制的人工
证据错误平移到稳定版，采用两次冻结：

1. `v1.11.0-rc.8` 只用于最后一次收尾演练和发现代码问题；
2. RC8 演练无代码问题后，将版本提升为最终 `1.11.0` 并冻结；
3. 所有正式人工、物理设备、下载、安装和发布证据都绑定最终 `1.11.0` 提交、Manifest、
   ZIP、Setup.exe 和 EXE 哈希；
4. RC8 的探索证据可以帮助发现问题，但不能替代稳定版正式回执。

### 1.2 Windows 采用 unsigned 分发

项目当前没有 Windows Authenticode 商业代码签名证书。v1.11.0 明确采用：

- `distribution_channel=unsigned`；
- `signed=false`；
- `publisher_identity=unverified`；
- README、Release Notes 和安装说明公开披露 SmartScreen 可能提示；
- 用户只应从项目 GitHub Release 下载并核对 SHA-256；
- 不伪造签名状态，不用测试证书冒充公开发布者身份。

Windows Authenticode 与以下两类 RSA 签名不是同一件事：

- 应用更新清单 RSA 签名用于防止更新元数据和下载包被篡改；
- 插件市场发布者 RSA 签名用于验证 `.lpak` 发布者与包内容。

本轮只明确延期 Windows Authenticode。更新清单签名继续使用本机受控私钥，私钥不得进入
仓库或发布产物。若当前没有经过批准的插件市场发布者身份，则 LPWP 签名参考包和生产远程
市场发布作为 v1.12 生态发布项延期，不得伪造通过。

### 1.3 单机、单维护者验收

当前没有第二台电脑，也没有独立审核人。发布流程必须如实记录：

- `review_model=single_maintainer`；
- `independent_review=false`；
- 风险接受人、时间、原因和适用版本；
- 操作人与审核人是同一维护者时不得填写两个虚构姓名；
- 将来获得独立审核人后，可以追加更严格的复核，但不能改写历史决策。

干净环境按以下优先级取得：

1. Windows Sandbox；
2. 本机 Hyper-V、VMware 或 VirtualBox 新建 Windows VM；
3. 同一台机器的新 Windows 本地用户；
4. 当前日常用户只能用于探索，不得称为“干净环境”。

同一物理电脑不等于同一系统环境。证据必须记录隔离类型、Windows 版本、用户 SID 摘要、
虚拟化方式、预装运行时和测试前快照。若只能使用新本地用户，最终报告必须披露其隔离强度
低于全新 VM。

### 1.4 v1.11.0 的外部生态范围

v1.11.0 稳定版的核心范围是 Long助手宿主、统一入口、统一工作区、25 个内置插件、本地插件
平台、本地/内置市场目录、安装更新链和 LPWP Long助手侧合同。

以下外部生态能力只有在真实依赖可用时才进入 v1.11.0 强制门禁：

- Long Grid 跨仓库 E2E；
- 正式插件市场发布者身份和签名参考包；
- 生产 HTTPS Registry/CDN 部署。

若冻结稳定版前仍没有 Long Grid 仓库、批准的插件发布者身份或生产凭据，则必须：

1. 在代码、设置和文档中把对应能力标记为 Preview、Disabled 或 Deferred；
2. 从核心稳定版强制放行集合中移出，但在最终决策记录 `deferred`，不能记录 `passed`；
3. 保留现有协议、验证器和实验实现，不删除已经完成的工程成果；
4. 将真实生态发布转入 v1.12，不阻塞 v1.11.0 核心稳定版。

## 4. 每一步统一开发、审计与推送规则

从本文合并后开始，禁止继续直接向 `master` 连续提交。每个批次必须遵循：

1. 从最新 `origin/master` 创建 `agent/v1-11-<阶段>-<主题>` 分支；
2. 一个分支只解决一个可验收问题；
3. 修改代码时同步增加或更新自动化测试；
4. 更新 `docs/当前开发状态.md`，记录提交前事实、验证和下一接手点；
5. 本地执行相关专项、Release 构建和全量测试；
6. 只暂存本批文件，不提交 `artifacts/**` 原始截图、录像、ETL、私钥或令牌；
7. 创建 Draft PR，写清根因、变化、风险、验证结果和候选影响；
8. 等待 `Build and test` 与 `Plugin platform` 全部通过；
9. 检查 PR Diff、未跟踪证据和版本身份后再合并；
10. 合并后确认 `master == origin/master`，记录 CI URL 和合并提交；
11. 任何失败先修复并重新验证，不在文档中提前写“已完成”。

稳定版冻结提交之后，只允许提交两类哈希回执：

- `docs/plugin-manual-approvals/*.json`；
- `docs/final-validation-approvals/*.json`。

普通文档、脚本、版本、代码或资源的任何变化都使候选失效，必须重新冻结。

## 5. S1：退出链与稳定性最后开发

### S1A 结构化退出可观测性

> 2026-08-13 执行状态：已完成。代码、14 项定向测试、1415 项全量测试、Release 构建和真实宿主清理探针全部通过；四个顶层步骤均为 `passed`，宿主退出码 0，本次派生 WebView2 / Worker 最终残留为 0。下一阶段为 S1B。详细证据映射见 [`v1.11.0-S1A退出可观测性审计_2026-08-13.md`](v1.11.0-S1A退出可观测性审计_2026-08-13.md)。

目标：让每次宿主退出都能回答“哪一步用了多久、是否超时、失败后是否继续”。

开发内容：

1. `BestEffortShutdownSequence` 返回所有步骤结果，而不只返回失败列表；
2. 每项记录 `name`、`status`、`elapsed_ms`、`timeout_ms` 和稳定错误分类；
3. 区分 `passed`、`failed`、`timed_out`；
4. 记录迟到任务最终成功或失败，不保存敏感异常正文到公开报告；
5. 宿主质量启动参数支持输出不可覆盖的 shutdown JSON；
6. `verify-host-process-cleanup.ps1` 要求该报告存在并验证步骤集合。

验收目标：

- Broker、Plugins、Plugin Runtime、Host Services 四个顶层步骤全部出现；
- 正常退出每一步状态为 `passed`；
- 合成失败和超时仍会执行后续步骤；
- 报告绑定源码提交、宿主 EXE SHA-256、PID 与退出码；
- 新增成功、失败、超时、迟到完成和不可覆盖测试。

### S1B 插件关闭整体预算

> 2026-08-13 执行状态：代码、15 项退出链定向测试、1419 项全量测试和 Release 构建已完成；正式宿主已接入单插件 3 秒与整体 20 秒预算。真实宿主清理证据必须在本批合并后的干净提交上重新生成，通过前不进入 S1C。详细映射见 [`v1.11.0-S1B插件关闭整体预算审计_2026-08-13.md`](v1.11.0-S1B插件关闭整体预算审计_2026-08-13.md)。

当前每插件预算为 3 秒且串行执行，极端情况下 25 个插件可能累计到约 75 秒。开发目标是：

1. 保留单插件预算；
2. 增加整体关闭预算，建议硬上限 20 秒；
3. 每个插件实际等待不超过“单插件预算”和“剩余整体预算”的较小值；
4. 整体预算耗尽后记录未完成插件 ID，不静默成功；
5. 宿主仍继续完成安全可执行的资源释放；
6. 迟到插件不得重新修改 Registry 状态、健康状态、自动启动偏好或 UI；
7. 不通过并行关闭引入新的系统副作用竞争。

验收目标：

- 单个失联插件不会阻塞后续插件；
- 多个失联插件不会让宿主超过整体预算；
- 正常 25 插件退出不出现超时；
- 真实宿主目标退出时间不超过 15 秒，硬门槛不超过 30 秒；
- 退出后本次宿主派生 WebView2 / Worker 残留为 0。

### S1C 稳定性复跑

关闭正在运行的安装版 Long助手后，对最新 Release 宿主执行：

- 真实退出与子进程清理；
- 16 轮 WebView 会话创建/释放；
- 12 轮工作区多模块切换；
- 三插件组合空闲趋势；
- 嵌入与独立插件混合生命周期；
- 前台、隐藏、托盘交替；
- 锁屏/解锁、睡眠/唤醒、显示器变化的探索性验证。

资源目标：

- 后台隐藏期不发生持续宿主 API 轮询；
- CPU 不超过现有 6% 自动门槛；
- 句柄、线程、私有内存最长连续上升不超过 3 个采样间隔；
- 20 插件工作集继续 `<200 MB`，达到 `>=190 MB` 时记录预警；
- 全部插件会话、窗口、模块和子进程最终清理。

S1 完成后，除发现的阻断缺陷外，不再继续修改 UI 或新增功能。

## 6. S2：发布政策与门禁代码对齐

### S2A unsigned 稳定版合同

验收目标：

- 版本为稳定 `1.11.0` 时仍允许 `unsigned` 通道；
- Manifest 必须如实记录 `signed=false` 与 `publisher_identity=unverified`；
- Setup.exe 不请求管理员权限；
- README 与 Release Notes 展示 SmartScreen 和 SHA-256 提示；
- 自动更新清单仍必须通过独立 RSA 签名与包哈希验证；
- Windows 代码签名缺失不能被记录为“已签名”。

### S2B 单维护者风险接受模式

现有最终外部门禁要求下载操作人与审核人不同。不得通过填写两个名字绕过。需要新增显式模式：

```text
review_model=single_maintainer
independent_review=false
risk_accepted_by=<真实维护者>
risk_accepted_at=<UTC 时间>
risk_reason=no_second_machine_or_independent_reviewer
```

代码要求：

- 默认仍采用严格独立审核；
- 单维护者模式必须显式开关、完整风险接受字段和稳定版号；
- 最终决策醒目标记缺少独立复核；
- 不允许空姓名、自相矛盾身份或复用其他版本风险接受；
- 测试覆盖严格模式拒绝、单维护者显式通过和伪造身份拒绝。

### S2C 外部生态延期合同

如果稳定版冻结时仍缺少 Long Grid 仓库、插件发布者身份或生产 Registry/CDN：

- `lpwp-long-grid-e2e`、`lpwp-signed-reference`、`production-marketplace-rehearsal`
  使用 `deferred`，不是 `passed`；
- 最终决策必须列出延期原因、目标版本和功能默认状态；
- Long Grid/远程生态入口不得误导用户为已经正式可用；
- 本地插件安装、内置目录和 Long助手侧 LPWP 合同仍必须通过；
- 相关验证脚本继续保留，v1.12 可恢复为强制门禁。

### 10.2 DPI 与辅助功能

在同一台物理机器顺序切换 100%、125%、150%、200% 缩放，每档完成亮暗主题要求的 8 张
正式截图，总计 32 张。不得用离屏缩放伪装物理设置。

辅助功能覆盖：

- High Contrast；
- Reduced Motion；
- Combined；
- 至少一轮 Narrator；
- UIA Focus 与 Live Region 事件；

## 11. S7：最终聚合与 GitHub 稳定发布

### 11.1 最终产品摘要

稳定版核心范围完成后生成 `approved_final_product_acceptance`。若外部生态延期，摘要必须同时
记录三项延期，不得从 JSON 中直接删除事实。

### 11.2 外部发布决策

先运行只读预检，再生成不可覆盖正式决策：

```powershell
.\verify-external-release-gate.ps1 <稳定版证据参数> -PreflightOnly
.\verify-external-release-gate.ps1 <稳定版证据参数> -OutputPath <新路径>
```

目标输出：

- `classification=external_release_gate_decision`；
- `passed=true`；
- `source_commit` 为稳定版冻结提交；
- `distribution_channel=unsigned`；
- `review_model=single_maintainer`；
- `independent_review=false`；
- 所有核心必需项通过；
- 外部生态延期项及风险接受完整披露。

### 11.3 GitHub Release

1. 创建 `v1.11.0` 标签，精确指向冻结提交；
2. 上传 Setup.exe、两个 ZIP、Manifest、SHA256SUMS 和更新清单；
3. 先以 GitHub Prerelease 状态公开，用真实浏览器完成最终下载检查；
4. 资产发布后不得覆盖；发现代码或二进制问题时废弃该版本并进入 `1.11.1`；
5. 全部正式门禁通过后，只切换同一 Release 的 Prerelease 状态为稳定，不更换标签或资产；
6. 标记为 Latest，并再次核对远端资产大小、Digest 和本地 SHA-256。

## 12. S8：发布后复核

发布后在当前安装版执行：

- 自动更新发现 `v1.11.0`；
- 更新清单 RSA 验证通过；
- 下载包 SHA-256 通过；
- 用户确认后安装；
- 设置、插件数据和快捷方式保持；
- GitHub Release 页面、README、CHANGELOG 和安装文档版本一致；
- 记录已知限制：unsigned、单维护者验证、外部生态延期。

## 13. 失败回退规则

- 代码、脚本、资源或普通文档变化：候选立即失效，重新冻结；
- 仅新增合规批准回执：候选保持有效；
- 人工项目失败：保留失败证据，修复根因，不修改回执伪装通过；
- RC8 失败：创建 RC9，不覆盖 RC8；
- 已公开 `v1.11.0` 资产失败：保留并标记废弃，修复后使用 `v1.11.1`；
- 证据采集中断：使用新目录重采，不补写缺失 Manifest；
- 无外部凭据：记录延期，不填写假地址、假签名或假审核人；
- 不删除历史 Release、标签、批准回执或本机原始证据来“重做同一版本”。

## 14. 用户需要参与的项目

维护者可以自动完成代码、脚本、构建、测试、打包、哈希、CI 和大部分桌面探针。用户需要参与：

1. 允许关闭当前运行中的安装版 Long助手，执行退出门禁；
2. 对 25 个插件的真实结果做最终判断；
3. 在 Windows 设置中切换四档 DPI、高对比度和减少动画；
4. 启动 Narrator 并判断公告是否可理解；
5. 在管理员终端完成 WPR 采集；
6. 允许配置 Windows Sandbox、VM 或新本地用户；
7. 确认 SmartScreen 和杀毒软件实际显示；
8. 明确接受 unsigned 与单维护者发布风险；
9. 若未来提供 Long Grid、插件发布者密钥或生产 Registry 凭据，再恢复延期生态门禁。
