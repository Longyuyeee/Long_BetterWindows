## 3. 与最初设计的对齐

1. **契约优先**：先建立 Manifest、输入、输出、权限、执行与持久化协议，再开放编辑和导出界面，符合最初核心架构原则。
2. **统一能力边界**：工作流复用现有命令与宿主能力，不引入第二套插件 API，也不兼容或复制外部插件协议。
3. **本地优先**：工作流、报告和导出均保留在本机；没有引入账号、云同步或后台远程执行。
4. **权限可见**：执行前绑定定义指纹、插件版本和能力集合；敏感输出查看与落盘分别批准。
5. **失败安全**：可变步骤要求补偿，执行失败按策略逆序恢复；仓储和导出使用原子文件操作且拒绝静默覆盖。

总体方向与最初设计一致。当前偏差是产品入口尚未完全统一，而不是协议或安全方向偏离。

## 4. 当前缺口与风险

1. **外部发布门禁未完成人工签核**：SmartScreen、杀毒软件、干净 Windows、物理 DPI、真实屏幕阅读器和生产 Registry/CDN 仍需要受控环境与独立审核人。
2. **组合动作仍是 Tool Center 内的独立工作台**：已保存工作流尚未进入统一命令目录和超级面板，距离“统一入口、低步骤执行”的原始体验目标还有一段集成工作。
3. **视图代码再次增长**：`WorkflowEditorControl.xaml.cs` 约 960 行，领域逻辑已经模块化，但运行批准、结果、报告、导入导出等 WPF 编排仍集中；继续增加入口前应先拆协调边界。
4. **真实 UI 验收不足**：领域与契约测试充分，但终端输出长文本、窄布局、键盘焦点、文件对话框拒绝路径仍需语义化 UI Automation 和人工视觉复核。不得恢复屏幕坐标自动点击。
5. **高级工作流语义尚未定义**：条件、并行、重试、定时和无人值守会改变权限时效、补偿顺序与报告模型，目前不应直接实现。

## 5. 推荐后续顺序

1. 完成或明确延期 v1.9 外部人工发布门禁，保持 RC 与后续主线边界不变。
2. 提取工作流运行/结果协调模块，降低 WPF code-behind 对领域会话、导出器和报告仓储的直接编排。
3. 设计“托管工作流命令投影”契约：只发布已保存、当前可读取且预检有效的工作流；插件目录变化后动态失效；搜索结果明确标识组合动作和步骤数。
4. 从统一命令中心与超级面板触发时，复用现有执行审查界面，继续展示插件版本、能力、可变步骤和敏感终端输出选项。
5. 补齐真实交互验收后，再做复制/模板/参数预设；不优先增加新插件、条件分支或云同步。
