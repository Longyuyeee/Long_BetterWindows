# Long窗口 组合动作编排协议

> 状态：基础协议阶段
> 主线：`master`
> 发布边界：不属于已冻结的 `v1.9.0-rc.1` 候选包

## 1. 目标

组合动作把现有统一命令连接为可审计的顺序工作流。首要目标不是可视化编辑器，而是先建立稳定的执行契约：

1. 所有命令在执行前完成全量解析和输入兼容性检查。
2. 权限审查覆盖正向命令与补偿命令涉及的全部插件、插件版本和宿主能力。
3. 可变步骤在补偿模式下必须声明逆操作，失败后才能进行确定性的逆序恢复。
4. 工作流身份绑定步骤、输入、参数、插件版本和能力集合，敏感输入只参与 SHA-256 指纹，不写入权限摘要。
5. 执行结果提供逐步骤时间线，供日志、诊断和未来编辑器使用。

## 2. 当前协议

`CommandWorkflowDefinition` 包含：

- 稳定工作流 ID 和展示名称。
- `Stop` 或 `Compensate` 失败策略。
- 1 至 32 个有序步骤。

每个 `CommandWorkflowStep` 包含：

- 唯一步骤 ID。
- `ReadOnly` 或 `Mutating` 副作用分类。
- 正向 `WorkflowCommand`。
- 可选补偿命令；补偿模式中的可变步骤必须提供。

每个命令继续复用 `PluginCommandInvocation`，不建立第二套文本、文件、图片或结构化参数协议。

## 3. 预检与权限边界

`CommandWorkflowPlanner` 在任何命令执行前完成：

1. 工作流 ID、步骤 ID、步骤数量和重复项检查。
2. 正向与补偿命令存在性检查。
3. `command_id` 与目标命令一致性检查。
4. 输入类型与插件声明的 `accepted_inputs` 兼容性检查。
5. 可变步骤补偿完整性检查。
6. 插件 ID、版本和能力集合汇总。
7. 生成小写 64 位 SHA-256 权限审查指纹。

参数字典按键名排序后参与指纹，因此字典插入顺序不会制造不同身份；文本、路径、图片和参数值变化会使指纹失效。插件版本或能力集合变化也会使旧权限审查失效。

## 4. 失败恢复原则

下一实现阶段的执行器遵循以下规则：

1. 预检未通过时零命令执行。
2. `Stop` 模式在首个失败步骤停止，不宣称回滚。
3. `Compensate` 模式只补偿已经成功完成的步骤，并严格逆序执行。
4. 补偿是尽力执行；单个补偿失败不能阻止其余补偿，但最终状态必须是 `CompensationFailed`。
5. 取消与普通失败分别记录；取消发生后仍按既定策略处理已完成步骤。
6. 只读步骤不强制声明补偿，也不能被描述为已回滚的写操作。

`CommandWorkflowExecutor` 每次执行都会重新预检。调用方必须提供 `CommandWorkflowAuthorization`，其工作流指纹、插件 ID、插件版本和能力集合必须与本次预检完全一致，否则以 `Rejected` 结束且零命令执行。

每个插件注册实例具有独立代次，重新注册会获得新值，普通启动/停止状态变化不会使审批失效；无关插件的注册变化也不会打断当前工作流。执行器在每个正向步骤前重新预检；若参与插件升级、重新注册、能力变化或工作流内容变化导致指纹漂移，后续步骤不会执行。此时旧批准不能授权新插件实现执行补偿，结果会明确标记 `CompensationFailed`，保留现场供人工恢复。

工作流定义未来可以持久化，`CommandWorkflowAuthorization` 则明确为当前宿主会话内的一次权限快照，不跨应用重启或参与插件重新注册复用。

补偿不复用已经取消的正向执行令牌，而是为每个逆操作创建独立的 30 秒恢复窗口。单个补偿失败后仍继续执行剩余逆操作，最终通过 `CompensationFailed` 明确暴露部分恢复风险。

执行结果包含单调递增序号、UTC 时间、步骤 ID、阶段和非输入型结果消息。事件不记录命令文本、路径、图片或参数内容。

## 5. 暂不实现

- 可视化流程编辑器和拖拽连线。
- 条件分支、循环、并行分支和跨设备执行。
- 后台无人值守批准。
- 用通用编排补偿替代插件安装或注册表已有的专用事务机制。

这些能力必须在顺序执行、权限审批、取消和补偿时间线稳定后再评估。

## 6. 持久化与来源信任

工作流文档当前使用 Schema v3，包含 `schema_version`、`source` 和 `workflow`。Schema v2 以原来源和空绑定语义迁移；Schema v1 可以迁移，但迁移结果固定为 `legacy-v1` 未信任导入，不继承任何历史可信声明。

来源分为：

- `LocalManaged`：由本机托管仓储创建，只表示来源可追踪。
- `Imported`：从外部文件或模板目录导入，默认 `Untrusted`。
- `TrustedSource`：外部信任策略中的 `source_id` 与规范化工作流定义 SHA-256 精确匹配。

文件内自报 `LocalManaged` 或可信来源不能提升信任等级。定义哈希绑定步骤、命令、补偿、文本、路径、图片和排序后的参数，但不包含当前插件注册代次；执行时仍必须重新预检并取得会话级 `CommandWorkflowAuthorization`。

文本、路径、图片和参数均按潜在敏感输入处理。文件仓储默认拒绝静默保存这些字段，只有明确选择包含敏感输入时才允许落盘。

编辑会话通过主命令/补偿命令角色更新结构化 invocation，并按插件 `accepted_inputs` 严格校验输入类型；`None` 不再绕过命令契约。集合与图片数据在进入草稿时复制，避免外部可变引用改变已预检定义。

外部导入分为预览与采用两步。预览只读取、迁移、判定来源信任并执行预检，不改变当前草稿或托管目录；采用后生成没有本地定义哈希的未保存草稿，因此同 ID 文件不能绕过乐观并发保护覆盖本地工作流。`TrustedSource` 仅描述来源与定义哈希匹配，仍须完成会话级执行授权。

`CommandWorkflowRepository` 只在本机托管根目录保存工作流，使用同目录临时文件、写穿透、落盘刷新和原子替换，避免半写文件。文档上限为 4 MB，并使用严格 UTF-8 解码；托管根目录、目标文件和导入文件均拒绝重解析点。已有工作流的更新必须提交加载时获得的定义 SHA-256，同一仓储实例内的并发更新通过串行化校验保证只有当前版本可以覆盖。

导出只接受已保存且无待处理更改的托管工作流，并要求提交当前定义 SHA-256。导出目标必须位于托管目录外；文件在目标目录写穿透、刷新后原子替换。导出 Envelope 的来源固定改写为 `Imported` 与 `<local-source>:export`，定义哈希保持不变，但重新导入时默认仍为 `Untrusted`，不会携带本机托管信任。

导入操作只解析外部文件，不创建托管目录、不复制文件，也不生成执行授权。外部文件即使自报 `LocalManaged` 仍按未信任处理；只有外部策略精确允许的 `source_id + definition SHA-256` 可以标记为 `TrustedSource`，且执行前仍需重新预检和会话批准。

执行报告使用独立 Schema v1，绑定报告 ID、工作流 ID、规范化定义 SHA-256、执行指纹、最终状态、时间区间和有序事件。报告默认清除顶层结果消息及全部事件消息；只有调用方显式选择保留消息，并在保存时再次批准潜在敏感内容，仓储才允许落盘。报告文件上限为 1 MB，采用严格 UTF-8、同目录原子创建和不可覆盖语义，不保存会话授权对象。

结构化输出只允许 `Text` 与 `Path` 两种类型，并由插件通过独立输出字典返回；结果消息仍只用于用户反馈。绑定结构包含来源步骤、输出键、目标类型及可选参数键，最多 64 项，只能引用执行顺序中已经可用的步骤。主命令可引用前序步骤；补偿命令可额外引用自身主命令的成功输出。文本目标最多一个，参数目标键必须唯一，路径目标可按绑定顺序形成多路径输入。绑定结构参与定义哈希和授权指纹，运行时值不参与静态授权，也不写入脱敏报告。

执行器在每个成功命令后立即复制并校验输出，限制为 64 项、64 字符标识符键和 65,536 字符值；Path 输出不能为空。缺失输出、类型不匹配或解析后超过 invocation 路径/参数上限均使当前步骤失败。补偿命令使用相同输出校验，解析失败会标记该补偿失败并继续更早的补偿。任何输出值都不进入执行事件或报告。
